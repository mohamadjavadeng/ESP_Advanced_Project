0 Your Project at a Glance

Understand what you have before you write. This project has strong publication potential.

⚙

Core System

A dual-ESP32 + Raspberry Pi architecture for real-time excavation depth monitoring. Two ESP32 devices measure bucket arm angles (IMU sensors) and stream raw data over WiFi to a Raspberry Pi hub, which computes dig depth in real-time and displays results on a DWIN LCD.

👁

AI / Computer Vision

YOLOv4-tiny and YOLOv8n object detection for person safety monitoring around the excavation zone. EZVIZ IP camera integration with RTSP streaming, person-zone alarm detection, and automatic WhatsApp alert notifications with snapshot images.

📡

IoT & Communication

WiFi AP/STA dual-mode networking between ESP32s and RPi. RFID (RC522) access logging. Geofencing with GeoBox token verification. Multi-protocol data flow: UDP/TCP sensor streams, MQTT-style pub/sub, REST API on the Pi.

📈

Monitoring & Dashboard

Real-time excavation monitoring with depth calculations, alarm management, sensor health checks, and a comprehensive Raspberry Pi dashboard. Geolocation tracking and excavation site mapping.

Publication Angle: This project combines embedded IoT, edge AI inference, and industrial safety — a hot topic in conferences like IEEE IoT, WF-IoT, or industrial AI workshops. The dual-architecture evolution (ESP32-centric → RPi-centric) also makes an interesting design study.

3 How to Write Each Section

Detailed guidance with specific content mapped to your repository files.

Abstract (Write Last)

A self-contained summary. Follow this formula:

// Sentence 1: Context + Problem Excavation-related accidents remain a leading cause of workplace injuries in the construction industry, with limited real-time monitoring solutions available. // Sentence 2: What you built This paper presents a low-cost, real-time excavation monitoring and worker safety system that integrates dual ESP32 microcontroller sensor nodes with a Raspberry Pi edge computing hub. // Sentence 3: Key methods The system continuously computes bucket depth using IMU-derived angular data streamed over WiFi, while a YOLO-based computer vision pipeline monitors worker proximity to dangerous excavation zones. // Sentence 4: Key results (use real numbers from your experiments) Experimental evaluation demonstrates depth measurement accuracy within ±2cm at update rates of 10Hz, with person detection achieving 89% mAP at 8 FPS on edge hardware. // Sentence 5: Impact The proposed system provides an affordable, scalable safety solution suitable for small-to-medium construction sites.

Introduction

  • Paragraph 1 — Problem Statement Excavation hazards: cave-ins, struck-by, utility strikes. Cite OSHA/BLS statistics. Emphasize that current solutions are expensive (e.g., Leica, Trimble machine control) and not accessible for small contractors.
  • Paragraph 2 — Existing Solutions & Gap Briefly mention commercial systems (GNSS-based machine control, laser-guided depth). Explain why they fail for small sites: cost ($50K+), complexity, GPS dependency in urban areas.
  • Paragraph 3 — Your Approach Introduce your dual-ESP32 + RPi architecture. Highlight: low cost (ESP32 ~$5, RPi ~$35), no GPS dependency, real-time edge computing, integrated AI safety monitoring.
  • Paragraph 4 — Contributions List 3-4 specific contributions. E.g.:
    • A low-cost dual-node IMU-based depth estimation system
    • Real-time WiFi sensor streaming architecture for field deployment
    • Edge AI person-detection safety monitoring with automated alerts
    • Open-source integrated platform for construction site safety
  • Paragraph 5 — Paper Organization "The remainder of this paper is organized as follows..." (1-2 sentences)

Related Work

  • Subsection A: IoT for Construction Safety Review papers on IoT-based construction site monitoring. Search Google Scholar for: "IoT construction safety monitoring", "smart construction site", "wearable sensors construction". Aim for 8-10 references.
  • Subsection B: Excavation Monitoring Systems Review depth measurement approaches: sonar-based, GNSS-based, IMU-based, laser-based. Search: "excavation depth monitoring", "earthmoving equipment sensing", "machine control system". 5-8 references.
  • Subsection C: Edge AI for Safety Review YOLO-based safety detection in construction. Search: "object detection construction safety", "YOLO worker detection", "edge AI construction". 5-8 references. Highlight the gap: most use cloud-based processing, few do real-time edge inference.
  • Subsection D: Your Positioning 1 paragraph summarizing the gap: existing systems either focus on depth OR safety, not both; they use expensive hardware; they lack edge computing. Your system addresses all three.

System Design & Architecture

This is your main contribution section. Reference your actual source code and hardware.

  • Architecture Overview Describe the RPi-centric architecture (current version). Key files to reference internally: esp32_ap_client/src/main.cpp (ESP32 node), ESP32_IP_Connection/src/main.cpp (IP connection), monitoring_control.py (RPi hub). Include an architecture diagram (see Phase 4).
  • ESP32 Sensor Nodes Describe: IMU sensor for angular measurement, WiFi connection to RPi AP, raw angle streaming over UDP/TCP. Mention the evolution from ESP32-centric to RPi-centric design as a design lesson learned. Include pseudocode of the sensor reading loop.
  • Communication Protocol Describe the WiFi AP/STA setup (ap_sta_setup.py), data format (angle packets), latency considerations. Show a sequence diagram of data flow: ESP32 → WiFi → RPi → Computation → LCD display.
  • Depth Computation Algorithm Explain the trigonometric computation. Use actual equations. Show how two angles (arm angle + bucket angle) translate to depth. Include the mathematical model with variables defined. This is a key technical contribution.
  • DWIN LCD Interface Briefly describe the DGUS-based LCD for real-time depth display on the excavator. Reference the HMI design images and dwin_lcd.py. Show how operators see live depth readings.

AI-Based Safety Monitoring

  • Object Detection Pipeline Describe YOLOv4-tiny / YOLOv8n deployment on RPi. Key files: person_detector.py, model_ncnn.py, yolov8n_ncnn_model/. Report model size, quantization (NCNN), inference time. Include a table: model vs. mAP vs. FPS vs. memory.
  • Person-Zone Alarm System Describe the EZVIZ camera integration, RTSP streaming (rpi_stream.py), danger zone definition, and alarm triggering (rpi_person_zone_alarm.py). Include a diagram of camera FOV + danger zones.
  • Alert & Notification Describe automated WhatsApp alerts with snapshot images (send_alarm.py). Discuss the end-to-end latency from detection to notification. Show example alarm images (from your alarms/ folder).

Implementation & Experiments

Critical: This section makes or breaks your paper. You need to run actual experiments and report real numbers. Here's what to measure:
  • Depth Accuracy Place a reference marker at known depths. Compare system readings vs. ground truth. Compute MAE, RMSE, max error. Report for different depths (e.g., 0.5m, 1.0m, 1.5m, 2.0m). Create a table + scatter plot.
  • Angle Measurement Accuracy Calibrate IMU readings against a protractor/level. Report angular error in degrees. Test at different orientations.
  • System Latency Measure: ESP32 sensor read → WiFi transmit → RPi compute → LCD update. Use timestamps or oscilloscope. Report average, P95, P99 latencies.
  • Detection Performance Run YOLO on test images/video from your camera. Compute mAP@0.5, precision, recall. Test at different distances, lighting conditions. Report FPS and inference time per frame.
  • Network Reliability Test WiFi signal strength at different distances (10m, 30m, 50m, 100m). Report packet loss rate, reconnection time. Test with obstacles (typical construction site).
  • Power Consumption Measure ESP32 current draw. Estimate battery life for portable deployment. Compare with power consumption of commercial alternatives.
  • Cost Analysis Bill of materials: 2x ESP32 ($10), RPi 4 ($35), IMU sensors ($8), DWIN LCD ($25), EZVIZ camera ($40), RFID reader ($5), misc ($20). Total ~$143. Compare with commercial systems ($50K+).

Discussion

  • Design Trade-offs Why RPi-centric over ESP32-centric? (Computational power, ML framework support, easier development). Trade-off: higher cost, more power consumption, less rugged.
  • Limitations Be honest: WiFi range limitation in construction sites, RPi not ruggedized, YOLOv4-tiny accuracy vs. larger models, no GNSS integration, calibration requirements.
  • Scalability Could this scale to multiple excavators? Multiple cameras? Cloud dashboard? Discuss what would be needed.

Conclusion & Future Work

  • Summarize contributions in 3-4 sentences (mirror the Introduction)
  • Restate key experimental results
  • Future work: GNSS integration, 5G connectivity, larger YOLO models, cloud dashboard, multi-machine coordination, fatigue detection via face analysis

4 Required Figures & Diagrams

Visuals are critical. A good paper has 6-10 figures. Here's what to create.

📐

Fig. 1: System Architecture

Show the full system: 2 ESP32 nodes → WiFi → RPi Hub → LCD + Camera + Dashboard + WhatsApp. Use Draw.io or TikZ. This is your most important figure.

📏

Fig. 2: Physical Setup

Photo of the actual hardware setup on an excavator arm or test rig. Show ESP32 mounting, IMU placement, LCD on the cab. A real photo is worth more than a diagram.

📈

Fig. 3: Depth Computation Model

Geometric diagram showing excavator arm angles, trigonometric relationships, and how depth is derived. Label all variables used in your equations.

📊

Fig. 4: Depth Accuracy Results

Scatter plot: computed depth vs. ground truth. Include regression line and R² value. Or bar chart of error at different depths.

👁

Fig. 5: Detection Pipeline

Diagram: Camera → RTSP Stream → Frame Grab → YOLO Inference → Bounding Boxes → Zone Check → Alarm. Show with example output image.

📷

Fig. 6: Detection Examples

Sample output images showing person detection with bounding boxes in danger zones. Include true positive and edge cases. From your alarms/ directory.

🕑

Fig. 7: Sequence / Timing Diagram

Data flow timeline: ESP32 reads sensor → packets sent → RPi receives → computes → sends to LCD. Show actual measured timestamps.

💰

Fig. 8: Cost Comparison

Bar chart comparing your system cost (~$143) vs. commercial alternatives ($50K-$200K). Dramatic visual impact for reviewers.

Tools for figures: Use Draw.io / diagrams.net for architecture diagrams, Python matplotlib for data plots, TikZ for LaTeX papers, Inkscape for vector graphics. For photos, use a clean background and add labels/arrows.

5 Formatting & Submission

Technical details that affect acceptance.

LaTeX Setup

Download the IEEE template from overleaf.com (search "IEEE Journal" or "IEEE Conference"). Use IEEEtran.cls. Set column layout, fonts, and margins per conference specs. Most conferences provide their own template — always use the official one.

Citation Management

Use Zotero or Mendeley to manage references. Export as .bib file. Use \cite{author2024} format. IEEE uses numbered citations [1], [2]. Aim for 25-40 references; at least 60% from last 5 years.

Common Rejection Reasons

✓ Weak experimental validation
✓ Insufficient comparison with prior work
✓ Poor figures / hard to read
✓ Grammar / language issues
✓ Missing limitations discussion

Submission Checklist

☐ PDF meets page limit
☐ All figures are high-res (300 DPI+)
☐ References are complete
☐ Author names anonymized (if blind review)
☐ Supplementary materials ready (code repo)

6 Writing Timeline (8 Weeks)

A realistic schedule from start to submission. Adjust based on your conference deadline.

Week 1 — Preparation

Research & Setup

Select target conference. Download template. Read 5 recent papers. Set up Overleaf/LaTeX project. Begin literature search (Google Scholar, IEEE Xplore). Create a shared BibTeX file.

Week 2 — Experiments

Run All Benchmarks

Execute depth accuracy tests, run YOLO on test footage, measure latency, document network performance, photograph hardware setup. Collect all raw data and create initial plots.

Week 3 — First Draft

Write Sections IV & V (System Design + AI)

Write the core technical sections first. These are the heart of your paper. Include equations, pseudocode, and reference your figures. These sections will be 40% of your paper.

Week 4 — Extended Draft

Write Sections III & VI (Related Work + Experiments)

Write related work with proper citations. Write experiments section with all tables, figures, and analysis. Ensure every claim has experimental backing.

Week 5 — Complete Draft

Write Introduction, Conclusion, Abstract

Write introduction (set up the problem, state contributions). Write conclusion. Write abstract last. Add discussion section with limitations. First complete draft should be ready.

Week 6 — Review & Polish

Internal Review

Read the entire paper aloud. Fix grammar (use Grammarly). Verify all figures are clear and labeled. Check equation numbering. Ensure consistent notation. Ask a colleague to review.

Week 7 — Finalize

Incorporate Feedback & Final Edits

Address all reviewer comments from internal review. Finalize figures. Format references perfectly. Prepare supplementary materials (code, dataset). Create a brief demo video if allowed.

Week 8 — Submission

Final Check & Submit

Final PDF check (page limits, margins, file size). Double-check author information. Submit 2-3 days before deadline. Do NOT submit on the last day — servers crash.
