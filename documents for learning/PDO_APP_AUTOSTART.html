1. The premise, corrected

The request opened with "it doesn't save the camera IP". It was saving it, every 60 seconds without a miss. Checked before changing anything:

journalctl -u rpi-cam-find.service -n 12
15:53:24  camera 0c:a6:4c:b7:64:ea at 192.168.50.25 (matched dhcp_name='H8c_BF9010198_EZVIZ', live now)
15:54:24  camera ... live now
15:55:24  camera ... live now

cat /var/lib/rpi-ap-sta/camera.env
CAMERA_IP=192.168.50.25
CAMERA_LIVE=1

The real gap was that nothing read that file. The address was sitting on disk, correct and current, while the launch command still carried --ip 192.168.50.25 typed by hand. So the work was not discovery — it was wiring.

Worth separating

"The data is missing" and "nothing consumes the data" feel identical from the outside — in both cases the app has no IP. Checking which one it is takes one cat and decides whether you build a producer or a consumer. Building the wrong one is a day lost.

2. The shape of the problem

The manual routine was:

cd ~/Project/PDO/finalCode && source ~/venv/bin/activate
python control_monitoring2.py --device-id excavator1 --http-host 192.168.50.1 \
       --hse-host 127.0.0.1 --alarm-buzzer off --push-interval 0.5 &
python rpi_person_zone_alarm.py --ip 192.168.50.25

Three constraints are hiding in there, and each one becomes a rule in the automation.

a. There is a real ordering dependency

Not a preference. Reading the sources settles who waits for whom:

# control_monitoring2.py -- it BINDS and listens
srv.bind((self.args.hse_host, self.args.hse_port))
srv.listen(1)
# on failure: _set_camera_status("DISABLED: cannot bind ...")  <- no retry

# rpi_person_zone_alarm.py -- it CONNECTS out
self.sock = socket.create_connection((host, port), ...)
# "best-effort with ONE silent reconnect per send: a down link must never..."

Monitoring owns the socket, the detector dials in. So monitoring goes first. But note the second half: the detector reconnects on its own. That single fact later decides a dependency direction (§5c).

b. The bind address must exist before the bind

--http-host 192.168.50.1 is the AP's own address, which NetworkManager puts on uap0 during boot. Bind to an address the kernel does not own yet and it fails — and this app does not retry, it just records DISABLED and runs on without an HSE server. A race that costs a few seconds to avoid, or the whole feature to ignore.

c. The camera's address is unknown at launch time

Which is the interesting one. It is not merely unknown at boot — it may be unknown for hours, because the camera can be switched off. Anything that treats "no camera yet" as an error will crash-loop for as long as the site is quiet.

3. What was already on the Pi

Two disabled units turned up, which is why nothing was created until they had been read:

systemctl list-unit-files | grep -iE 'pdo|monitor|excav|alarm'
excavator-controller.service    disabled
excavator-detector.service      disabled

They were an earlier attempt at exactly this job. Four things made them unusable rather than a starting point:

In the old unitProblem
ExecStart=/usr/bin/python3 ...System interpreter, not ~/venv/bin/python. The venv is where cv2, flask, serial and RPi.GPIO actually live.
control_monitoring.py --no-cameraThe original script, two versions behind control_monitoring2.py.
No --ip at allFalls back to the script default 192.168.100.67 — an address from a different network entirely.
ExecStartPre=/bin/sleep 8A guess standing in for a readiness check. Fine on a good day; wrong whenever the camera takes nine seconds.

They were left in place, still disabled, rather than deleted — see §11.

The pattern to take from this

sleep 8 is the tell. Wherever a fixed sleep appears in a unit file, there is a real condition somebody chose not to express: an address appearing, a port answering, a file being written. Name the condition and wait for it, and the fragility goes away instead of moving.

4. How it works now

5. Seven design decisions, and why

a. A wrapper script, not ExecStart with a variable

The obvious approach is EnvironmentFile=/var/lib/rpi-ap-sta/camera.env and ExecStart=... --ip ${CAMERA_IP}. It does not work, for a reason worth internalising: systemd expands an EnvironmentFile once, at unit start. At that moment the camera may be minutes away, or off for the weekend. The value we need does not exist yet, and the wait must be unbounded — so it has to happen inside a process, which means inside a wrapper.

b. Absolute interpreter path, no source activate

PDO_PY=/home/rpi4/venv/bin/python
exec "$PDO_PY" "$MONITOR_SCRIPT" ...

Activating a venv only prepends its bin to PATH. Calling that interpreter directly achieves the same thing and cannot be undone by whatever PATH systemd hands the unit. Verified which venv first — /home/rpi4/venv has cv2, numpy, flask, serial, PIL, RPi.GPIO, openpyxl; /home/rpi4/myenv is empty and would have failed on the first import.

c. Wants=, deliberately not Requires=

The old unit used Requires=excavator-controller.service. That reads as correct — no detector without a controller — but it means every monitoring restart tears the detector down too, throwing away a loaded YOLOv4-tiny model and ~30 s of startup. And it is unnecessary, because AlarmLink reconnects on its own (§2a). So:

After=pdo-monitoring.service rpi-cam-find.service uap0.service
Wants=pdo-monitoring.service rpi-cam-find.timer

Starting the detector still pulls monitoring up with it; a monitoring bounce no longer touches the detector. Test 1 below measures exactly this.

d. SuccessExitStatus=3

The finder exits 3 for "AP healthy, camera simply not here". Without declaring that a success, systemd marks the unit failed every 60 s while the camera is off — a journal full of red that trains you to ignore the journal.

e. Gate on the RTSP port, not just on presence

A camera can hold a DHCP lease and answer ARP while its RTSP server is still starting. The detector would then spend its --attempts 5 --wait 4 budget on a device that was 10 s from ready. One extra condition removes that:

timeout 2 bash -c "exec 3<>/dev/tcp/$CAMERA_IP/554"

This is not hypothetical — it fired on the very first cold boot (§8).

f. Distinguish "known" from "present"

A DHCP lease outlives the device that held it, so the state file can name a camera that is switched off. CAMERA_LIVE carries that distinction and the gate honours it:

camera 192.168.50.25 is known but not currently on the AP (CAMERA_LIVE=0)

g. Restart the detector when the IP moves

The detector receives --ip in its argv, fixed for the life of the process. If DHCP hands the camera a different address, the detector cannot notice — it just talks to nobody. The finder can notice, so it acts:

if [ -n "$prev_ip" ] && [ -n "$ip" ] && [ "$prev_ip" != "$ip" ]; then
    log "camera moved $prev_ip -> $ip; restarting the detector"
    systemctl try-restart pdo-person-alarm.service || true
fi

try-restart rather than restart: it acts only if the unit is already running, so it is a no-op when the detector is deliberately stopped.

7. The tests, including the two that were wrong

Five tests. Two of them initially proved nothing, and both failures were in the test rather than the system — recorded here because the mistakes are more instructive than the passes.

Test 1 — a monitoring restart must not disturb the detector PASS

detector PID before: 9974
sudo systemctl restart pdo-monitoring.service
detector PID after : 9974        <- same process, model not reloaded
detector NRestarts : 0
16:03:05  [hse-link] armed (camera client 127.0.0.1:45224 connected)
16:03:05  [INFO] alarm link connected to 127.0.0.1:5050

The link re-established itself two seconds after monitoring returned. Confirms the Wants= choice in §5c.

Test 2 — hard kill must recover and re-resolve the address PASS

sudo kill -9 9974
NRestarts=1
10155 /home/rpi4/venv/bin/python rpi_person_zone_alarm.py --ip 192.168.50.25
16:03:52 armed — watching for a person in the zone
16:04:00 alarm link connected to 127.0.0.1:5050

Test 3 — camera absent: must wait, not crash-loop two false passes first

Attempt 1. Pointed CAM_PATTERN at a name that matches nothing, marked CAMERA_LIVE=0, restarted the detector. It logged the correct wait message and then started 25 s later — apparently a pass. It was not: the restore had not happened yet. What ended the wait was the finder's own carry-forward logic, which recognises the camera by MAC and re-marked it live, correctly, because the camera was still physically on the AP. The test had not simulated an absent camera at all.

Attempt 2. Tried to block the finder with systemctl mask:

Failed to mask unit: File '/etc/systemd/system/rpi-cam-find.service' already exists

A unit whose file lives in /etc/systemd/system cannot be masked — masking wants to put a /dev/null symlink at that exact path. The finder ran, carry-forward revived the camera again.

Attempt 3. Removed the prior record as well, so carry-forward had nothing to carry — which is precisely the cold-boot-with-camera-off state. Also switched from pgrep to the unit's own MainPID, because pgrep -cf 'rpi_person_zone_alarm' was matching the SSH command line that contained the pattern and reporting phantom processes.

MainPID: 10920 -> bash /usr/local/sbin/pdo-person-alarm-run.sh   <- the gate, not python
NRestarts: 0
16:08:35  waiting: no camera address in /var/lib/rpi-ap-sta/camera.env yet
16:09:35  waiting: no camera address in /var/lib/rpi-ap-sta/camera.env yet

... camera restored ...
16:11:00  camera ready at 192.168.50.25 -- starting rpi_person_zone_alarm.py
16:11:03  armed
16:11:11  alarm link connected to 127.0.0.1:5050
MainPID: 10920 -> /home/rpi4/venv/bin/python rpi_person_zone_alarm.py --ip 192.168.50.25

PASS Waited 2 m 25 s. NRestarts stayed 0, the wait message appeared once a minute rather than every poll, the PID never changed (the wrapper execed in place), and the transition needed no intervention.

Three ways a test lies, all seen here
  1. The system self-heals faster than you can measure. Carry-forward is a feature; it also silently repaired the condition under test. To test a fallback you must disable every path that fixes it.
  2. Your own command matches your own probe. pgrep -f X run from a shell whose command line contains X counts itself. Ask systemd for MainPID instead.
  3. Timing races in the harness. A later systemctl start of an already-running oneshot collapses into the in-flight run — which still had the old config — so the "restore" never took effect inside the observation window. Verified by reading the timestamps, not by assuming.

Test 4 — the IP-change hook PASS

Faked a stale recorded address so the next scan sees a move:

sudo sed -i 's|^CAMERA_IP=.*|CAMERA_IP=192.168.50.99|' /var/lib/rpi-ap-sta/camera.env
sudo /usr/local/sbin/rpi-cam-find.sh
camera 0c:a6:4c:b7:64:ea at 192.168.50.25 (matched dhcp_name='H8c_BF9010198_EZVIZ', live now)
camera moved 192.168.50.99 -> 192.168.50.25; restarting the detector to pick up the new address
detector PID: 10920 -> 11407     restarted with the correct address

NRestarts stays 0 here, correctly — an explicit try-restart is not a failure-restart, and systemd counts only the latter.

8. Cold-boot evidence

Both units enabled, full reboot, nothing typed afterwards:

uptime: up 2 minutes

uap0.service              active   restarts=0
rpi-cam-find.timer        active
pdo-monitoring.service    active   restarts=0
pdo-person-alarm.service  active   restarts=0

1435 python control_monitoring2.py --device-id excavator1 --http-host 192.168.50.1 \
          --hse-host 127.0.0.1 --alarm-buzzer off --push-interval 0.5
1436 python rpi_person_zone_alarm.py --ip 192.168.50.25

LISTEN  192.168.50.1:5000   pid=1435
LISTEN  127.0.0.1:5050      pid=1435
ESTAB on 5050: 2

The argv is character-for-character the manual command, with --ip supplied by the machine. The timeline is the part worth reading:

16:13:05  starting control_monitoring2.py (device=excavator1 http=192.168.50.1)
16:13:08  [main] HTTP on 192.168.50.1:5000
16:13:08  [hse-link] waiting for camera client on 127.0.0.1:5050
16:13:07  waiting: camera 192.168.50.25 is on the AP but RTSP/554 is not answering yet
16:13:19  camera ready at 192.168.50.25 -- starting rpi_person_zone_alarm.py
16:13:37  armed — watching for a person in the zone
16:13:44  alarm link connected to 127.0.0.1:5050
16:13:44  [hse-link] armed (camera client 127.0.0.1:39652 connected)
The RTSP gate paid for itself immediately

At 16:13:07 the camera had already rejoined the AP and held its lease — every presence check would have said "ready" — but its RTSP server was not up for another twelve seconds. The old sleep 8 would have handed the detector a camera that was not listening yet. Waiting for the port instead of a duration cost nothing and removed the failure entirely.

pdo-wait-ap logged nothing, which is the correct outcome: it only reports when it actually had to wait, and 192.168.50.1 was already present on its first check.

9. Daily use

The whole routine is now nothing, since both units are enabled at boot. When you do need to drive it:

pdo status          # what is up, where the camera is, which processes exist
pdo start | stop | restart
pdo logs            # follow both apps and the finder together
pdo logs alarm      # or: monitoring | cam
pdo ip              # prints just the camera IP, for use in scripts

To change any argument, edit one file and restart — no unit files involved:

sudo nano /etc/default/pdo-apps
sudo systemctl restart pdo-monitoring pdo-person-alarm

Reading the IP from your own code, in preference order:

. /var/lib/rpi-ap-sta/camera.env   # CAMERA_IP, CAMERA_MAC, CAMERA_RTSP, CAMERA_LIVE
cat /run/rpi-camera-ip             # the IP alone
ping ipcam                         # /etc/hosts alias, kept current
Before running either app by hand again

sudo pdo stop first. Monitoring binds :5000 and :5050, and the HSE socket is listen(1) — a single slot. A second copy will not politely queue; it will fail to bind, or take the slot the service wanted.

10. Gotchas worth keeping

GotchaWhat to do instead
pgrep -f pattern counts your own shell when the pattern is in your command linesystemctl show -p MainPID --value unit, then ps -p $PID -o args=
systemctl mask fails for units living in /etc/systemd/systemStop the timer and remove the state it depends on, or move the unit file aside
systemctl start on an in-flight oneshot joins that run instead of forcing a new oneWait for it to finish, or run the script in the foreground when you need a fresh read of config
EnvironmentFile is read once at unit startAny value that appears later must be read inside the process — a wrapper
iw station dumps silently return nothing without root, and iw is not on the user PATHsudo, and set PATH=/usr/sbin:... at the top of scripts
A fixed sleep in a unit fileName the condition it stands for and poll that

11. Loose ends

  • excavator-controller.service and excavator-detector.service still exist, disabled. Harmless where they are, but they point at the old script with the wrong interpreter and a wrong camera IP, so anyone who enables them later will get a confusing failure. Say the word and they go.
  • Driver_name_database.xlsx is missing from finalCode/: [rfid] local file read failed: [Errno 2] No such file or directory. Pre-existing, and the app recovers by loading 2 tags from the cloud — but the local fallback is not there if the cloud is unreachable.
  • Cloud auth uses password login. The app warns: no --geomind-apikey set; falling back to PASSWORD login. This evicts the portal user and is revoked when anyone else logs in. Worth setting an API key.
  • The Pi and repo copies have diverged slightly. control_monitoring2.py on the Pi is 112076 bytes (Aug 2); raspberry_pi/monitoring_control.py in the repo is 112075 (Jul 29). Nothing was overwritten — the Pi's working copy was left alone deliberately. Reconcile them when convenient.
  • Standing risk from the AP work: the station is pinned to 2.4 GHz and eth0 is down, so a dead 2.4 GHz upstream means no way in. See AP_automation.html §10.
