Make the concurrent AP + station come back on every boot

The Pi is serving both roles right now, by hand. This is how it survives a reboot, a power cut, and a cold start on a slow SD card — automatically, unattended, with a way to prove it worked rather than hoping.

1What is missing right now

A working concurrent AP is four separate things, and typing them by hand makes all four temporary. Only the last one persists on its own:

PieceSurvives a reboot by itself?Why
The uap0 netdev (iw dev … interface add) NoVirtual interfaces are runtime-only. Nothing in the kernel or NetworkManager remembers it
Its distinct MAC (flipped locally-administered bit) NoDies with the interface. A fresh uap0 is born sharing wlan0's MAC again
The channel matching the station PartlyStored in the profile, but goes stale the moment the station joins a different router
The AP profile (NetworkManager) or hostapd.conf YesAlready on disk. But a profile with no interface to bind to just fails quietly

So the job is: recreate the interface at the right moment, give it the right MAC, let the existing profile bind to it, and keep the channel honest afterwards.

2The boot chain, in order

Order is the whole problem. Every boot failure in §8 is this sequence going wrong at one specific point.

power on │ ├─ 1 kernel + brcmfmac firmware load (slowest step on a cold SD card) │ └─▶ wlan0 netdev appears in /sys/class/net │ ├─ 2 YOUR UNIT RUNS HERE ◀── this is the whole trick │ iw dev wlan0 interface add uap0 type __ap │ ip link set uap0 address │ │ ⚠ must be BEFORE step 3. Once wlan0 is associated, brcmfmac │ answers "Device or resource busy (-16)" and refuses. │ ├─ 3 NetworkManager starts │ ├─ autoconnects the STATION profile on wlan0 → internet │ └─ autoconnects the AP profile on uap0 → SSID on the air │ + DHCP + NAT ├─ 4 channel follower re-pins the AP to the station's channel (t+90s, then /60s) │ └─ 5 your own program starts, bound to 0.0.0.0 so it answers on both interfaces

Confirm the two facts this relies on, on your own machine:

# NetworkManager orders itself after network-pre.target -- that is the hook we use
systemctl cat NetworkManager.service | grep -E '^(After|Before|Wants)='

# how long the radio takes to appear on YOUR sd card (step 1 above)
journalctl -b -k | grep -iE 'brcmfmac|wlan0: ' | head -8

3Which startup mechanism (and which fail)

"Can I not just put the command in a startup file?"

You can put it in several. Most of them run too late — after NetworkManager has already associated wlan0 — and then the one command that matters fails with EBUSY every single boot. This is the single most common reason a hand-built concurrent AP "works until I reboot".

MechanismRunsCreates uap0?Notes
systemd unit, Before=NetworkManager.service before NM touches the radioCorrect The only mechanism that is reliably early enough. Journal-logged, ordered, testable
udev rule → SYSTEMD_WANTS the instant wlan0 appearsCorrect Removes the device-unit race. Best used with the unit above, not instead — see §5
nmcli con modify … autoconnect yes when NM sees the deviceN/A Required, but it only reactivates the profile. It cannot create the interface the profile needs
NetworkManager dispatcher script on NM connectivity eventsToo late Genuinely useful for "once the AP is up, do X". Cannot create the interface early enough
crontab @reboot after multi-user.targetToo late Well after NM associated. EBUSY (-16), every boot
/etc/rc.local rc-local.service, after network.targetToo late Same failure, plus deprecated and not enabled by default on Bookworm
~/.bashrc, ~/.profile, autostart on interactive login onlyNever A headless Pi that reboots at 3am logs nobody in
The answer to "a command in startup code", precisely: one line, ExecStart=/usr/local/sbin/uap0-up.sh, in a unit carrying Before=NetworkManager.service. The Before= is not decoration — it is the load-bearing part. Everything else below is making that one line robust against a slow cold boot.

4Step by step — make it automatic

Ten steps. Nothing here disturbs the AP you have running; you are writing down what already works so the machine can redo it without you.

Step 1 — Snapshot the working state first

You are about to change boot behaviour on a machine that currently works. Capture it, so "it worked yesterday" is evidence rather than a memory.

mkdir -p ~/apsta-snapshot && cd ~/apsta-snapshot
iw dev                                     > iw-dev.txt
iw reg get                                 > reg.txt
ip -br addr                                > ip-addr.txt
ip -br link                                > ip-link.txt
nmcli con show                             > nm-list.txt      2>/dev/null
nmcli -f all con show rpi-ap               > nm-ap.txt        2>/dev/null
ls -l /etc/NetworkManager/conf.d/          > nm-confd.txt     2>/dev/null
sudo cp /etc/hostapd/hostapd.conf .                           2>/dev/null
systemctl list-unit-files | grep -E 'uap0|hostapd|dnsmasq|ap-' > units.txt
tar czf ~/apsta-snapshot.tgz -C ~ apsta-snapshot
echo "saved: ~/apsta-snapshot.tgz"

Step 2 — Identify which stack is serving the AP

The rest of the steps differ slightly. Find out which one you actually built.

nmcli -g GENERAL.STATE connection show rpi-ap 2>/dev/null \
  && echo "->> Route A: NetworkManager owns the AP"
systemctl is-active --quiet hostapd \
  && echo "->> Route B: hostapd owns the AP"
iw dev | grep -B4 'type AP'                      # confirm the AP iface name

Route A ⇒ do every step. Route B ⇒ do all steps but replace step 7 with step 7b.

Step 3 — Record the interface names once

One file, sourced by every script below, so a name change is a one-line edit rather than a hunt.

sudo tee /etc/default/rpi-ap-sta >/dev/null <<'EOF'
# Sourced by uap0-up.sh, ap-channel-follow.sh, ap-watchdog.sh, ap-boot-report.sh
STA_IFACE=wlan0
AP_IFACE=uap0
AP_TYPE=__ap
AP_CON=rpi-ap
EOF
cat /etc/default/rpi-ap-sta

If your AP interface is called something else (a USB dongle, wlan1), change AP_IFACE here and nowhere else.

Step 4 — The script that recreates the interface

Three jobs: wait for the radio, add the virtual netdev, give it a different MAC. Idempotent, so a rerun is harmless.

sudo tee /usr/local/sbin/uap0-up.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# Recreate the virtual AP netdev on the same physical radio as the station.
# Runs once per boot, BEFORE NetworkManager. Idempotent.
set -euo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
. /etc/default/rpi-ap-sta

rfkill unblock wlan || true

# A cold boot on a slow SD card can take many seconds to load brcmfmac firmware,
# and systemd .device units can lose that race. Wait for the radio explicitly
# instead of trusting unit ordering alone. 60s is generous on purpose: a boot
# that takes 20s once a year is cheaper than an AP that is missing until someone
# drives out to the machine.
for i in $(seq 1 60); do
    [[ -d /sys/class/net/$STA_IFACE ]] && break
    sleep 1
done
if [[ ! -d /sys/class/net/$STA_IFACE ]]; then
    echo "$STA_IFACE never appeared after 60s -- radio or firmware problem" >&2
    exit 1
fi
[[ ${i:-0} -gt 1 ]] && echo "waited ${i}s for $STA_IFACE"

# The concurrency trick: a second virtual netdev on the same PHY.
if ! iw dev | grep -qw "$AP_IFACE"; then
    iw dev "$STA_IFACE" interface add "$AP_IFACE" type "$AP_TYPE"
    echo "created $AP_IFACE on the $STA_IFACE radio"
fi

# Both netdevs inherit the one MAC of the one chip, and a shared MAC breaks ARP
# and DHCP for anything that joins the AP. Flip the locally-administered bit.
mac=$(cat "/sys/class/net/$STA_IFACE/address")
want="$(printf '%02x' $(( 0x${mac:0:2} ^ 0x02 )))${mac:2}"
if [[ "$(cat /sys/class/net/$AP_IFACE/address)" != "$want" ]]; then
    ip link set dev "$AP_IFACE" down
    ip link set dev "$AP_IFACE" address "$want"
    echo "set $AP_IFACE MAC to $want (station is $mac)"
fi
ip link set dev "$AP_IFACE" up
EOF
sudo chmod 755 /usr/local/sbin/uap0-up.sh
sudo bash -n /usr/local/sbin/uap0-up.sh      # syntax check only, changes nothing

Step 5 — The startup unit

This is the autostart. Every line in [Unit] is doing work — the annotations below the block explain which.

sudo tee /etc/systemd/system/uap0.service >/dev/null <<'EOF'
[Unit]
Description=Create uap0 virtual AP interface on the wlan0 radio
Documentation=file:///etc/default/rpi-ap-sta

# Order after the radio exists...
Wants=sys-subsystem-net-devices-wlan0.device
After=sys-subsystem-net-devices-wlan0.device

# ...and before anything configures the network. NetworkManager itself declares
# After=network-pre.target, so both of these put us ahead of it. Belt and braces:
# if one hook is missing on your systemd version, the other still holds.
Wants=network-pre.target
Before=network-pre.target NetworkManager.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/uap0-up.sh
ExecStop=-/usr/sbin/iw dev uap0 del

# A slow cold boot must not be killed halfway through the wait loop.
TimeoutStartSec=90

[Install]
WantedBy=multi-user.target
EOF

sudo systemd-analyze verify /etc/systemd/system/uap0.service   # silence = valid
DirectiveWhat breaks without it
Before=NetworkManager.serviceThe critical one. Run after NM and iw … interface add fails with EBUSY (-16) because wlan0 is already associated. No AP, every boot
Before=network-pre.targetNothing, if the line above holds. It is the idiomatic hook for "configure interfaces before networking", and covers the case where NM is socket-activated rather than started directly
After=sys-subsystem-net-devices-wlan0.deviceThe script can start before the radio exists. Mitigated by the wait loop in step 4 — keep both
Type=oneshot + RemainAfterExit=yesWithout RemainAfterExit systemd marks the unit inactive the moment the script exits, so is-active lies and other units cannot depend on it
ExecStop=-/usr/sbin/iw dev uap0 delWithout it, systemctl restart uap0 leaves a stale interface. The leading - means "do not fail if it is already gone"
TimeoutStartSec=90systemd's default 90s happens to match, but stating it means a longer wait loop later will not be silently killed
WantedBy=multi-user.targetsystemctl enable has nothing to link. The unit exists but never runs at boot — a classic "why is it not starting" with no error anywhere

Step 6 — Enable it, and test it right now

sudo systemctl daemon-reload
sudo systemctl enable uap0.service
systemctl is-enabled uap0.service            # must print: enabled

# it is already satisfied (uap0 exists), so mark it active without re-creating anything
sudo systemctl start uap0.service
systemctl status uap0.service --no-pager

# prove the ordering actually took effect
systemctl list-dependencies --before uap0.service | grep -iE 'NetworkManager|network-pre'

That last command should list NetworkManager.service — meaning systemd has recorded "uap0 runs before NM". If it prints nothing, the Before= lines did not parse; re-check step 5 and daemon-reload.

Step 7 — Make NetworkManager reconnect the profiles by itself

The interface will exist at boot. Now make sure NM actually binds to it without being asked. autoconnect-retries 0 is the one people miss — the default gives up after four attempts, which is exactly what happens when uap0 appears a second later than NM expected.

# --- the AP profile ---
sudo nmcli connection modify rpi-ap \
     connection.autoconnect yes \
     connection.autoconnect-priority 10 \
     connection.autoconnect-retries 0 \
     connection.interface-name uap0

# --- the station profile (whatever wlan0 is using) ---
STA=$(nmcli -g GENERAL.CONNECTION device show wlan0 | head -1)
echo "station profile: $STA"
sudo nmcli connection modify "$STA" \
     connection.autoconnect yes \
     connection.autoconnect-retries 0 \
     802-11-wireless.powersave 2

# confirm both
nmcli -f NAME,DEVICE,AUTOCONNECT,AUTOCONNECT-PRIORITY connection show

Step 7b — Route B only: enable hostapd and dnsmasq in the right order

Skip if NetworkManager owns your AP. These two must not start before uap0 exists, or they fail once and stay dead.

for u in hostapd dnsmasq; do
  sudo mkdir -p /etc/systemd/system/$u.service.d
  sudo tee /etc/systemd/system/$u.service.d/override.conf >/dev/null <<'EOF'
[Unit]
After=uap0.service
Requires=uap0.service

[Service]
Restart=on-failure
RestartSec=5
EOF
done
sudo systemctl unmask hostapd          # Raspberry Pi OS ships it masked
sudo systemctl daemon-reload
sudo systemctl enable hostapd dnsmasq
systemctl is-enabled uap0.service hostapd dnsmasq

Route B also needs uap0-up.sh to assign the address itself, since there is no NM profile to do it — append ip addr flush dev "$AP_IFACE"; ip addr add 192.168.50.1/24 dev "$AP_IFACE" to the end of the script from step 4.

Step 8 — Keep the channel honest after boot

Boot is not the only moment things drift. The station roams; the AP must follow, or clients silently stop associating. If you already installed this from the setup guide, skip to step 9.

sudo tee /usr/local/sbin/ap-channel-follow.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# One radio cannot hold two channels (iw list -> '#channels <= 1'). When the
# station joins a router on a different channel the AP goes stale and clients
# silently stop associating. Re-pin and reactivate.
set -uo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
. /etc/default/rpi-ap-sta

# Serialise against ap-watchdog.sh so the two never call 'nmcli con up' at once.
mkdir -p /run/lock 2>/dev/null || true
exec 9>/run/lock/ap-health.lock || exit 0
flock -n 9 || exit 0

cur=$(iw dev "$STA_IFACE" info 2>/dev/null | awk '$1=="channel"{print $2}')
[ -z "${cur:-}" ] && exit 0

if [ "$cur" -gt 14 ]; then
    logger -t ap-follow "$STA_IFACE is on 5 GHz ch $cur; the 2.4 GHz AP cannot follow. Pin the upstream to 2.4 GHz or add a USB dongle."
    exit 0
fi

want=$(nmcli -g 802-11-wireless.channel connection show "$AP_CON")
[ "$cur" = "$want" ] && exit 0

logger -t ap-follow "$STA_IFACE moved to ch $cur (AP had ${want:-unset}) -- resyncing"
nmcli connection modify "$AP_CON" 802-11-wireless.band bg 802-11-wireless.channel "$cur"
nmcli connection up "$AP_CON"
EOF
sudo chmod 755 /usr/local/sbin/ap-channel-follow.sh

sudo tee /etc/systemd/system/ap-channel-follow.service >/dev/null <<'EOF'
[Unit]
Description=Re-sync the AP channel to the station channel
After=NetworkManager.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/ap-channel-follow.sh
EOF

sudo tee /etc/systemd/system/ap-channel-follow.timer >/dev/null <<'EOF'
[Unit]
Description=Check every minute whether the station changed channel

[Timer]
OnBootSec=90
OnUnitActiveSec=60

[Install]
WantedBy=timers.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now ap-channel-follow.timer
systemctl list-timers ap-channel-follow.timer --no-pager

Step 9 — A per-boot state line in the journal

Cheap and worth more than it looks: one log line per boot, so journalctl -t ap-boot becomes a reliability history you can read weeks later instead of arguing from memory.

sudo tee /usr/local/sbin/ap-boot-report.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# Log one line describing the AP+STA state, ~60s into each boot.
set -uo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
. /etc/default/rpi-ap-sta
ap=$(ip -4 -br addr show "$AP_IFACE" 2>/dev/null | awk '{print $3}')
st=$(nmcli -g GENERAL.STATE connection show "$AP_CON" 2>/dev/null)
sc=$(iw dev "$STA_IFACE" info 2>/dev/null | awk '$1=="channel"{print $2}')
ac=$(iw dev "$AP_IFACE"  info 2>/dev/null | awk '$1=="channel"{print $2}')
n=$(iw dev "$AP_IFACE" station dump 2>/dev/null | grep -c '^Station')
logger -t ap-boot "ap_ip=${ap:-NONE} profile=${st:-NONE} sta_ch=${sc:-none} ap_ch=${ac:-none} clients=${n:-0}"
EOF
sudo chmod 755 /usr/local/sbin/ap-boot-report.sh

sudo tee /etc/systemd/system/ap-boot-report.service >/dev/null <<'EOF'
[Unit]
Description=Log AP+STA state once per boot
After=NetworkManager.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/ap-boot-report.sh
EOF

sudo tee /etc/systemd/system/ap-boot-report.timer >/dev/null <<'EOF'
[Unit]
Description=Run the AP boot report 60s after boot

[Timer]
OnBootSec=60
AccuracySec=5s

[Install]
WantedBy=timers.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now ap-boot-report.timer
sudo systemctl start ap-boot-report.service       # write one line now
journalctl -t ap-boot -o short-iso --no-pager

A healthy line looks like ap_ip=192.168.50.1/24 profile=activated sta_ch=6 ap_ch=6 clients=2. Any line with ap_ip=NONE or mismatched channels is a boot that failed.

Step 10 — Persist the radio's country code

Easy to forget because it only bites on a fresh boot: with no regulatory domain the AP either refuses to start or beacons at minimum power. Set it in the OS, not just at runtime.

sudo raspi-config nonint do_wifi_country US       # your code: GB DE OM AE IR ...
iw reg get | head -3                             # must NOT say 'country 00: DFS-UNSET'
grep -i country /etc/default/crda 2>/dev/null; ls -l /var/lib/systemd/rfkill/ 2>/dev/null

5Hardening: udev, locks, watchdog

Trigger the unit from udev instead of racing a device unit

The wait loop in step 4 handles the race by brute force. This removes it: udev pulls the unit in at the exact moment wlan0 appears. Use it alongside the Before= ordering, not instead of it.

sudo tee /etc/udev/rules.d/70-uap0.rules >/dev/null <<'EOF'
# When the built-in radio's netdev appears, start the unit that adds uap0.
SUBSYSTEM=="net", ACTION=="add", KERNEL=="wlan0", TAG+="systemd", \
  ENV{SYSTEMD_WANTS}="uap0.service"
EOF
sudo udevadm control --reload-rules
udevadm test /sys/class/net/wlan0 2>&1 | grep -i systemd_wants   # confirm it matches

Do not put the iw command directly in RUN+=. udev kills long-running RUN programs and the whole event pipeline stalls behind them — hand off to a unit, as above.

A watchdog for runtime death, not just boot

Boot is solved above. This covers the AP dying hours later — a driver hiccup, a NetworkManager restart during apt upgrade, an interface that vanished. It deliberately does not touch the channel; that is the follower's job, and the shared flock keeps the two from colliding.

sudo tee /usr/local/sbin/ap-watchdog.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# Revive the AP if it disappears at runtime. Does NOT manage the channel --
# ap-channel-follow.sh owns that. Both take the same lock so they never race.
set -uo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
. /etc/default/rpi-ap-sta

mkdir -p /run/lock 2>/dev/null || true
exec 9>/run/lock/ap-health.lock || exit 0
flock -n 9 || exit 0

# 1. the netdev itself vanished
if ! ip link show "$AP_IFACE" &>/dev/null; then
    logger -t ap-watchdog "$AP_IFACE is gone -- recreating via uap0.service"
    systemctl restart uap0.service || { logger -t ap-watchdog "recreate FAILED"; exit 1; }
    sleep 2
fi

# 2. netdev is there but the profile is not activated
state=$(nmcli -g GENERAL.STATE connection show "$AP_CON" 2>/dev/null)
if [ "${state:-}" != activated ]; then
    logger -t ap-watchdog "profile $AP_CON is '${state:-missing}' -- reactivating"
    nmcli connection up "$AP_CON" || logger -t ap-watchdog "reactivate FAILED"
    exit 0
fi

# 3. activated but with no address (rare, and invisible without this check)
if ! ip -4 addr show "$AP_IFACE" | grep -q 'inet '; then
    logger -t ap-watchdog "$AP_IFACE has no IPv4 -- bouncing $AP_CON"
    nmcli connection down "$AP_CON"; nmcli connection up "$AP_CON"
fi
EOF
sudo chmod 755 /usr/local/sbin/ap-watchdog.sh

sudo tee /etc/systemd/system/ap-watchdog.service >/dev/null <<'EOF'
[Unit]
Description=Revive the concurrent AP if it dies at runtime
After=NetworkManager.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/ap-watchdog.sh
EOF

sudo tee /etc/systemd/system/ap-watchdog.timer >/dev/null <<'EOF'
[Unit]
Description=Check the AP every 2 minutes

[Timer]
OnBootSec=120
OnUnitActiveSec=120

[Install]
WantedBy=timers.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now ap-watchdog.timer
sudo /usr/local/sbin/ap-watchdog.sh && journalctl -t ap-watchdog -n 5 --no-pager
Add the same lock to the follower if you installed it from the setup guide before reading this — the two lines are already in step 8's version. Without the lock, both timers can call nmcli connection up in the same second and one fails harmlessly but noisily.

6Start your own program after the AP is ready

The AP coming back is only half of "it works after a reboot" — your server has to come back too, and not before the network it needs.

First, the shortcut that removes the problem: bind to 0.0.0.0, not to 192.168.50.1. A socket on 0.0.0.0 binds successfully whether or not uap0 has an address yet, and then answers on the AP and the station link. Flask: app.run(host="0.0.0.0", port=8080). Do this and your service needs no waiting at all — just After=NetworkManager.service.
the simple case — bound to 0.0.0.0 
sudo tee /etc/systemd/system/ap-server.service >/dev/null <<'EOF'
[Unit]
Description=Telemetry server for the ESP32s on the concurrent AP
After=NetworkManager.service uap0.service
Wants=uap0.service

[Service]
Type=simple
User=pi
WorkingDirectory=/home/pi/ESP_Advanced_Project/raspberry_pi
ExecStart=/usr/bin/python3 monitoring_control.py
Restart=always
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
EOF
sudo systemctl daemon-reload
sudo systemctl enable --now ap-server.service
journalctl -u ap-server -f

If you genuinely must bind the specific address

Some libraries insist. Then wait for the address — but degrade, do not deadlock: the helper exits 0 on timeout so Restart=always retries the service instead of the unit wedging forever.

sudo tee /usr/local/sbin/wait-for-ap.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# Block until the AP interface has an IPv4 address. Exits 0 either way: a service
# that refuses to start is worse than one that starts and retries.
set -uo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
. /etc/default/rpi-ap-sta
for i in $(seq 1 60); do
    if ip -4 addr show "$AP_IFACE" 2>/dev/null | grep -q 'inet '; then
        [ "$i" -gt 1 ] && echo "waited ${i}s for $AP_IFACE"
        exit 0
    fi
    sleep 1
done
echo "$AP_IFACE still has no IPv4 after 60s -- starting anyway" >&2
exit 0
EOF
sudo chmod 755 /usr/local/sbin/wait-for-ap.sh

# then add to your service's [Service] section:
#   ExecStartPre=/usr/local/sbin/wait-for-ap.sh
Do not use After=network-online.target for this. It waits for the station to reach connectivity, which on a field machine with no upstream router may be never. Your AP-side server does not need the internet to serve two ESP32s — coupling it to network-online.target turns a working local AP into a service that never starts.

7Prove it — test without rebooting, then soak

Test 1 — does NetworkManager reconnect the AP on its own?

This is the real test of step 7. Take the AP down and restart NM; do not bring it back up by hand. If autoconnect is right, it returns without you.

sudo nmcli connection down rpi-ap
sudo systemctl restart NetworkManager
sleep 15
nmcli -g GENERAL.STATE connection show rpi-ap     # must print: activated
ip -br addr show uap0

Test 2 — does the interface get recreated from nothing?

Destroys uap0 completely, then rebuilds it exactly the way boot will.

sudo systemctl stop uap0.service          # ExecStop deletes the interface
iw dev | grep -c uap0                     # expect 0

sudo systemctl start uap0.service         # what boot does
ip -br link show uap0 wlan0               # exists again, MACs still differ
sudo nmcli connection up rpi-ap
journalctl -u uap0 -n 15 --no-pager       # read what the script reported

Test 3 — the actual reboot

sudo reboot

# ---- after it comes back, touch nothing first, then: ----
journalctl -t ap-boot -o short-iso --no-pager | tail -3   # ap_ip=... profile=activated
systemctl is-active uap0.service
nmcli -g GENERAL.STATE connection show rpi-ap
iw dev wlan0 info | grep channel; iw dev uap0 info | grep channel

# did anything in the chain complain?
journalctl -b -u uap0 -u NetworkManager -t ap-follow -t ap-watchdog --no-pager \
  | grep -iE 'fail|error|busy|-16|refus' || echo "clean boot"

# how long the chain took, and what blocked it
systemd-analyze critical-chain NetworkManager.service
systemd-analyze blame | head -12

Test 4 — the soak test that actually matters

A warm reboot re-uses a warm cache and a spun-up SD card. The failures that strand a machine in the field are cold boots. Do at least three, with the power physically removed for 30 seconds each, and read the history afterwards:

# after each cold power cycle, this history should gain one healthy line
journalctl -t ap-boot -o short-iso --no-pager

# every line must show a real address and 'activated':
#   2026-08-04T09:12:03  ap-boot  ap_ip=192.168.50.1/24 profile=activated sta_ch=6 ap_ch=6 clients=2
# any 'ap_ip=NONE' is a failed boot -- read that boot's log:
journalctl -b -1 -u uap0 --no-pager

journalctl only keeps history across boots if the journal is persistent. Check with ls /var/log/journal; if it is missing, enable it: sudo mkdir -p /var/log/journal && sudo systemd-tmpfiles --create --prefix /var/log/journal. On an SD card this costs a little write wear and is worth it.

8Boot-only failures

These all share a signature: it works when you type it, and fails after a reboot. That signature always means ordering or timing.

SymptomCauseFix
journalctl -u uap0 -b shows Device or resource busy (-16) The unit ran after NetworkManager associated wlan0 The Before= lines are missing or did not parse. systemctl list-dependencies --before uap0.service must list NetworkManager.service. Also check you are not also creating it from cron or rc.local
uap0 exists after boot, but no SSID NM gave up autoconnecting before the interface appeared nmcli -g connection.autoconnect-retries con show rpi-ap must be 0 (infinite). The default 4 is not enough on a slow boot
systemctl status uap0 → inactive (dead), no error at all The unit was never enabled, or [Install] is missing systemctl is-enabled uap0.service; if it says static, the WantedBy= line is missing from step 5
Warm reboot fine, cold boot fails brcmfmac firmware load is slower from cold; the radio was not there yet Raise the wait loop in step 4 from 60 to 120 and TimeoutStartSec to 180. Confirm the real delay: journalctl -b -k | grep brcmfmac

AP up, clients get no IP after a reboot only Something else grabbed :53 before NM's internal dnsmasq systemctl is-enabled dnsmasq should be disabled on Route A. Keep the dnsmasq-base package, disable the dnsmasq service
Devices on the AP cannot reach each other after a reboot uap0 came back sharing wlan0's MAC ip -br link show wlan0 uap0 — addresses must differ. If they match, the MAC-flip block in step 4 is missing or exited early
Everything up, but your server is not listening It started before uap0 had an address and bound a specific IP Bind 0.0.0.0 (§6). If you cannot, add ExecStartPre=/usr/local/sbin/wait-for-ap.sh
Your service never starts at all After=network-online.target and there is no upstream router Remove it. Depend on uap0.service and NetworkManager.service instead
AP works for hours then dies, boot is fine Runtime failure, not a startup problem That is what the watchdog in §5 is for. Check journalctl -t ap-watchdog
Nothing wireless works after boot; rfkill shows a soft block Persisted rfkill state, usually alongside an unset country Set the country (step 10). uap0-up.sh already calls rfkill unblock wlan on every boot
Two units fighting; log shows repeated up/down Follower and watchdog both reactivating Both must take /run/lock/ap-health.lock. Add the two flock lines to whichever script lacks them

9Final checklist

Everything that must be true for an unattended boot. Run the whole block; anything that is not enabled / yes / 0 is a machine that will not come back on its own.

echo "--- units that must be enabled ---"
systemctl is-enabled uap0.service ap-channel-follow.timer ap-watchdog.timer \
                     ap-boot-report.timer 2>&1

echo "--- Route B only (skip if NetworkManager owns the AP) ---"
systemctl is-enabled hostapd dnsmasq 2>&1

echo "--- NM profiles must autoconnect, and retry forever ---"
nmcli -f NAME,DEVICE,AUTOCONNECT connection show
for p in rpi-ap; do
  echo "$p retries: $(nmcli -g connection.autoconnect-retries con show $p)"   # want 0
done

echo "--- regulatory domain must be set ---"
iw reg get | head -2

echo "--- your own service ---"
systemctl is-enabled ap-server.service 2>&1

echo "--- ordering recorded by systemd ---"
systemctl list-dependencies --before uap0.service | grep -i networkmanager

echo "--- last boot's verdict ---"
journalctl -t ap-boot -o short-iso --no-pager | tail -1

10Rollback

Removes the autostart only. The AP keeps running until you reboot, and the profile, hostapd.conf and your station link are untouched.

sudo systemctl disable --now ap-watchdog.timer ap-channel-follow.timer \
                             ap-boot-report.timer ap-server.service 2>/dev/null
sudo systemctl disable uap0.service            # leave it RUNNING, just not at boot
sudo rm -f /etc/udev/rules.d/70-uap0.rules
sudo udevadm control --reload-rules
sudo systemctl daemon-reload

# confirm: the AP is still up, but nothing will bring it back next boot
iw dev | grep -A3 uap0
systemctl is-enabled uap0.service              # disabled

To remove it completely as well, delete the units and scripts:

sudo rm -f /etc/systemd/system/{uap0.service,ap-channel-follow.service,ap-channel-follow.timer} \
           /etc/systemd/system/{ap-watchdog.service,ap-watchdog.timer} \
           /etc/systemd/system/{ap-boot-report.service,ap-boot-report.timer} \
           /etc/systemd/system/ap-server.service \
           /usr/local/sbin/{uap0-up.sh,ap-channel-follow.sh,ap-watchdog.sh} \
           /usr/local/sbin/{ap-boot-report.sh,wait-for-ap.sh} \
           /etc/default/rpi-ap-sta
sudo systemctl daemon-reload
sudo iw dev uap0 del 2>/dev/null
iw dev                                          # only wlan0 remains
