Who is on my AP? — listing, naming and finding devices

The Pi's access point is up and things are joining it. This is how to see them all with IP, MAC, vendor and name — and how to answer the hard version of the question: which of these IPs is my camera?

"Can I scan all the connected devices to my AP with IP and name? I connected an IP cam whose name is H8c-**** and I want to know which IP is that device."

1The three tools

FileAnswersReach for it when
ap-clients.sh Who is on the AP, and what IP does this device have? Everyday. This is the one you will use
onvif-find.py What do the cameras call themselves? You need a camera's own advertised name, not just its MAC
apsta-doctor.sh Why can nothing join the AP at all? The list is empty, or a device refuses to connect

ap-clients.sh invents nothing. It joins four sources the kernel and the DHCP server already maintain:

iw dev uap0 station dump ──▶ MAC, signal, connected time (802.11 associations) DHCP lease file ──▶ MAC, IP, hostname the client asked for ip neigh show dev uap0 ──▶ IP ⇄ MAC, including static-IP devices with no lease IEEE OUI table (offline) ──▶ vendor: "Hangzhou XiongMai", "Espressif", ... │ ▼ one table, keyed by MAC

2Install them on the Pi

from Windows / PowerShell
$src = "C:\Users\Asus\Documents\GitHub\ESP_Advanced_Project\documents for learning\rpi_wifi_control"
scp "$src\ap-clients.sh" "$src\onvif-find.py" "$src\apsta-doctor.sh" pi@raspberrypi.local:~/
on the Pi — put them on PATH so you can just type the name
sudo install -m 755 ~/ap-clients.sh    /usr/local/sbin/ap-clients
sudo install -m 755 ~/onvif-find.py    /usr/local/sbin/onvif-find.py
sudo install -m 755 ~/apsta-doctor.sh  /usr/local/sbin/apsta-doctor

sudo ap-clients --help
Keep the .py on the ONVIF one. ap-clients finds it by looking for a file literally called onvif-find.py next to itself. Install it as onvif-find and the --onvif flag silently stops working (it prints a note to stderr and carries on without ONVIF names).

The rest of this page writes sudo ap-clients …. If you skipped the install step, use sudo bash ~/ap-clients.sh … instead — identical.

4Why "name" is the hard part

Finding IPs and MACs is easy — the kernel hands them over. Getting a name is where it gets interesting, because there is no single thing called "the device's name". There are four different names, and a cheap IP camera may broadcast none of them.

Kind of nameWhere it livesDoes a cheap IP cam send it?
The label on the box — e.g. H8c-**** Printed on the device. Usually its SoftAP SSID / cloud UID Not sent over the LAN at all
DHCP hostname (option 12) The lease file, once it asks for an address Often blank, or something useless like IPC
mDNS / Bonjouravahi-browse -art Rarely
ONVIF scopesWS-Discovery reply, UDP 3702 Usually — and it often is the box label
This is the key insight for the H8c-**** question. That string is on the sticker, not on the wire — so grepping the DHCP leases for "H8c" will usually find nothing. The two things that do work: ask the camera over ONVIF (--onvif), or identify it physically once with --find and then write the name down yourself with --alias. After that, every lookup is exact and needs neither.

So --ip matches your pattern against five sources, most trustworthy first:

#SourceTrust
1Your alias in /etc/rpi-ap-sta-hostsYou set it. It never lies
2ONVIF advertised name (only with --onvif)The device's own idea of its name
3DHCP hostname the device asked forAbsent on much cheap gear
4IEEE OUI vendor stringIdentifies the chipset maker, not the device
5The MAC or the IP itselfExact, but you have to know it

* in the pattern is a wildcard; anything else is a plain case-insensitive substring. Both of these work, and the shorter one is usually the better bet:

sudo ap-clients --ip H8c            # substring -- matches H8c-A1B2C3
sudo ap-clients --ip 'H8c-*'        # wildcard  -- same result
sudo ap-clients --ip xiongmai       # by vendor, when the device has no name at all
sudo ap-clients --ip 12:34:56       # by MAC prefix

5ap-clients.sh — every mode

default — the table

sudo ap-clients
sudo ap-clients --onvif        # + ask the cameras their names (adds ~5s)

Warms the ARP table first (so silent devices appear), then joins all four sources. The NAME column shows the best available name using the ladder above.

--ip PATTERN — print only the IP

sudo ap-clients --ip H8c
sudo ap-clients --ip 'H8c-*' --onvif
192.168.50.42

Bare IPs, one per line, nothing else — so it pipes and substitutes cleanly. Exit status is 0 if something matched, 1 if not, which is what makes this safe in a script:

if CAM=$(sudo ap-clients --ip gate-cam); then
    ffplay -rtsp_transport tcp "rtsp://user:pass@$CAM:554/"
else
    echo "camera is not on the AP right now"
fi

If several devices match, you get several lines. Narrow the pattern, or take the first with | head -1.

--show PATTERN — the matching rows

sudo ap-clients --show esp32
IP               MAC                VENDOR                   NAME                SIGNAL
192.168.50.51    aa:bb:cc:00:00:01  Espressif Inc.           esp32-stick            -40
192.168.50.52    aa:bb:cc:00:00:02  Espressif Inc.           esp32-beam             -45

Same matching as --ip, but human-readable. Use it to confirm you matched the right thing before wiring --ip into a script.

--find — the only certain method

sudo ap-clients --find
Baseline -- every device currently on uap0:
    12:34:56:78:9a:bc 192.168.50.42
    aa:bb:cc:00:00:01 192.168.50.51

Now power-cycle ONLY the device you are looking for -- unplug the camera, count
to five, plug it back in. Do not touch anything else on the network.

Watching for up to 180s. Ctrl-C to stop.
..
>>> LEFT the network (this is your device powering down):
    MAC 12:34:56:78:9a:bc   IP 192.168.50.42   vendor Hangzhou XiongMai Tech
.....
>>> JOINED the network (this is your device coming back):
    MAC 12:34:56:78:9a:bc   IP 192.168.50.42   vendor Hangzhou XiongMai Tech   dhcp-name -

That IP belongs to the device you just power-cycled. Certain, not inferred.
Use this once per device, then never again. Names and vendor strings can be missing or misleading; a device that physically left the network when you unplugged it cannot be anything else. It also prints the exact dhcp-host= line to give that MAC a permanent IP — see §8.

--alias <mac|ip> <name> — write the name down

sudo ap-clients --alias 192.168.50.42 gate-cam        # by current IP
sudo ap-clients --alias 12:34:56:78:9a:bc gate-cam    # or by MAC, which never changes
added: 12:34:56:78:9a:bc -> gate-cam
/etc/rpi-ap-sta-hosts now:
    # MAC                friendly-name
    12:34:56:78:9a:bc  gate-cam

From now on:  sudo bash /usr/local/sbin/ap-clients --ip gate-cam

Re-running with the same MAC updates the name rather than adding a duplicate. Passing an IP that is not currently on the AP fails with a clear message rather than writing a wrong entry.

sudo ap-clients --ports

RTSP on 554 is the strongest camera signal.
Open portUsually means
554RTSP — the strongest IP-camera signal there is
34567, 37777, 8899XiongMai / Dahua-style camera or DVR protocol
8000Hikvision SDK port
80, 8080A web UI — most cameras have one

This is inference. It is good at "that is a camera" and bad at "that is your camera" — use it to shortlist, then confirm with --find.

--json — for code, not eyes

sudo ap-clients --json
[
  {"ip":"192.168.50.42","mac":"12:34:56:78:9a:bc","vendor":"Hangzhou XiongMai Tech",
   "name":"gate-cam","dhcp_name":"","alias":"gate-cam","onvif":"",
   "signal_dbm":"-52","uptime_s":"8100"},
  {"ip":"192.168.50.51","mac":"aa:bb:cc:00:00:01","vendor":"Espressif Inc.",
   "name":"esp32-stick","dhcp_name":"esp32-stick","alias":"","onvif":"",
   "signal_dbm":"-40","uptime_s":"4210"}
]

Every field is a string, including the numbers — cast on your side. All values are JSON-escaped: a device that names itself ev"il\x cannot corrupt the document, which matters because the DHCP hostname is chosen by the client, not by you.

--watch — live

sudo ap-clients --watch      # re-prints every 3s; Ctrl-C to stop

Useful while walking a device around to check signal, or watching an ESP32 reconnect after a reset.

6Find your camera — the reliable recipe

Three commands, once. After this the camera has a stable name and a stable IP, and you never do detective work again.

# 1. Try the easy way first -- ask the cameras their own names.
sudo ap-clients --show H8c --onvif

# 2. Nothing? Identify it physically. Unplug the camera when prompted, plug it back in.
sudo ap-clients --find

# 3. Write the name down against the MAC it reported.
sudo ap-clients --alias 12:34:56:78:9a:bc H8c-cam

# From now on, this is exact and instant -- no ONVIF, no guessing:
sudo ap-clients --ip H8c-cam
--onvif camera answers with its own name? ──▶ done, you have the IP │ no ▼ --find unplug / replug, watch what leaves and returns │ ▼ --alias record MAC → name in /etc/rpi-ap-sta-hosts │ ▼ --ip name exact forever · survives reboots · survives a new DHCP lease │ ▼ dhcp-host= (optional, §8) same MAC always gets the same IP

7The alias file

/etc/rpi-ap-sta-hosts. One device per line: MAC, whitespace, name. Anything after # is a comment. --alias maintains it, but editing by hand is fine and often faster for several devices at once.

sudo tee /etc/rpi-ap-sta-hosts >/dev/null <<'EOF'
# MAC                friendly-name     # notes
12:34:56:78:9a:bc    H8c-cam           # IP camera, gate post, RTSP on 554
aa:bb:cc:00:00:01    esp32-stick       # angle sensor, stick
aa:bb:cc:00:00:02    esp32-beam        # angle sensor, beam
EOF
sudo ap-clients                        # NAME column now shows your labels
Key by MAC, not IP. A DHCP lease can change; a MAC will not. That is why --alias resolves an IP to its MAC before writing, and stores the MAC.

One caveat worth knowing: modern phones randomise their MAC per network for privacy, so a phone's MAC can change and an alias for it will go stale. The vendor column shows (randomised MAC) when it spots one. Cameras and ESP32s never do this.

8Pin a device to a fixed IP

Naming solves lookup. If you would rather the camera simply always be at the same address — so you can hard-code it in firmware or a config file — give it a DHCP reservation. NetworkManager reads extra dnsmasq settings for shared connections from /etc/NetworkManager/dnsmasq-shared.d/.

sudo mkdir -p /etc/NetworkManager/dnsmasq-shared.d
echo 'dhcp-host=12:34:56:78:9a:bc,192.168.50.90,ipcam' \
  | sudo tee /etc/NetworkManager/dnsmasq-shared.d/ipcam.conf

sudo nmcli connection down rpi-ap && sudo nmcli connection up rpi-ap

# power-cycle the camera so it asks for a new lease, then:
sudo ap-clients --show ipcam

Keep reservations outside the DHCP pool so they can never collide with a dynamic lease. With a pool of .10–.100, put reservations at .200+ — or shrink the pool:

# reservations at .200+, pool stays below it
echo 'dhcp-host=12:34:56:78:9a:bc,192.168.50.200,ipcam' \
  | sudo tee /etc/NetworkManager/dnsmasq-shared.d/ipcam.conf
echo 'dhcp-range=192.168.50.10,192.168.50.150,24h' \
  | sudo tee /etc/NetworkManager/dnsmasq-shared.d/pool.conf
sudo nmcli connection down rpi-ap && sudo nmcli connection up rpi-ap

Route B (hostapd + dnsmasq) instead: the same dhcp-host= line goes in /etc/dnsmasq.d/uap0.conf, then sudo systemctl restart dnsmasq.

9onvif-find.py

Sends a WS-Discovery Probe to UDP multicast 239.255.255.250:3702 out of the AP interface. ONVIF devices reply with "scopes" that normally carry the model and a friendly name — the one discovery method that returns a camera's own identity rather than just its MAC. Standard library only; no pip install.

sudo python3 /usr/local/sbin/onvif-find.py 192.168.50.1        # human output
sudo python3 /usr/local/sbin/onvif-find.py 192.168.50.1 10     # wait 10s instead of 5
sudo python3 /usr/local/sbin/onvif-find.py 192.168.50.1 --map  # ip⇥name⇥hardware
probing 239.255.255.250:3702 from 192.168.50.1, listening 5s ...

1 ONVIF device(s):

  192.168.50.42
    name       : H8c-A1B2C3
    hardware   : H8c
    urn        : urn:uuid:3fa1...
    device svc : http://192.168.50.42/onvif/device_service
    rtsp guess : rtsp://192.168.50.42:554/  (ask the device: GetStreamUri)

Match the 'name' or 'hardware' field against the label on your camera.
ArgumentMeaning
1st — source IPThe AP interface's own address. Defaults to 192.168.50.1. Required so the probe goes out of uap0 and not the default route
2nd — secondsHow long to listen. Default 5. Raise it if a camera is slow or the air is busy
--mapTab-separated, no prose. This is what ap-clients --onvif consumes

It sends three probes of each of two type-sets (NetworkVideoTransmitter, then empty for anything ONVIF) because UDP is lossy and budget cameras routinely drop the first probe. Exit code 2 means nobody answered.

Silence does not mean "not a camera". Plenty of cheap cameras ship with ONVIF disabled until you enable it in the vendor's phone app, and some only speak a proprietary cloud protocol. Fall back to --find, which needs no cooperation from the device.

10Use it from your own code

For monitoring_control.py or any Flask service on the Pi:

import json
import subprocess
import time

AP_CLIENTS = ["sudo", "-n", "/usr/local/sbin/ap-clients"]
_cache = {"at": 0.0, "devices": []}


def ap_devices(max_age=30.0):
    """Every device on the Pi's AP. Cached -- see the note about cost below."""
    if time.monotonic() - _cache["at"] < max_age:
        return _cache["devices"]
    try:
        r = subprocess.run(AP_CLIENTS + ["--json"],
                           capture_output=True, text=True, timeout=90)
        _cache["devices"] = json.loads(r.stdout) if r.returncode == 0 else []
    except (subprocess.TimeoutExpired, json.JSONDecodeError):
        pass                       # keep serving the last good answer
    _cache["at"] = time.monotonic()
    return _cache["devices"]


def ip_of(name):
    """IP of the device matching `name`, or None if it is not on the AP.

    Exit status 1 means no match -- that is the documented contract, not an error.
    """
    r = subprocess.run(AP_CLIENTS + ["--ip", name],
                       capture_output=True, text=True, timeout=90)
    if r.returncode != 0 or not r.stdout.strip():
        return None
    return r.stdout.strip().splitlines()[0]


cam = ip_of("H8c-cam")
if cam:
    stream = f"rtsp://user:pass@{cam}:554/"
Do not call this per HTTP request. Every invocation warms the ARP table first, which means an arp-scan sweep — or, without one installed, 253 pings. That is seconds, not milliseconds. Cache it, as above, and install arp-scan (§11) so the sweep is fast.

Running it from a non-root service

Your Flask app probably runs as pi, and the script needs root for station dump. Grant exactly that one command, nothing more:

sudo tee /etc/sudoers.d/ap-clients >/dev/null <<'EOF'
pi ALL=(root) NOPASSWD: /usr/local/sbin/ap-clients
EOF
sudo chmod 440 /etc/sudoers.d/ap-clients
sudo visudo -c                          # must say "parsed OK"

sudo -n /usr/local/sbin/ap-clients --json | head -3    # test as the pi user
Be aware what this grant actually permits: pi can run that script as root with any arguments, which includes --alias (writes /etc/rpi-ap-sta-hosts) and --ports (probes ports on the AP subnet). Nothing there is destructive, but it is broader than read-only. On a single-purpose machine where pi is you, that is a reasonable trade; on a shared box, wrap the specific call you need in your own tiny root script and grant only that instead.

12Troubleshooting the tools

SymptomCauseFix
Table is empty, no devices at all Nothing is associated, or the AP itself is broken sudo iw dev uap0 station dump. Empty too ⇒ this is an AP problem, not a tool problem: sudo apsta-doctor
Every VENDOR says unknown No OUI table on disk sudo apt install ieee-data (§11)
VENDOR says (randomised MAC) Not a fault — a phone using per-network privacy addresses Nothing to fix. Do not bother aliasing that MAC; it will change
NAME is - for a device It sent no DHCP hostname, and you have not aliased it Expected on cheap cameras. --find then --alias
--ip H8c finds nothing even though the camera is connected The H8c-**** label is not transmitted on the LAN (§4) Add --onvif. If still nothing, --find then --alias
