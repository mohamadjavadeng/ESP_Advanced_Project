1. The goal, and what already existed

The request was: make the Pi come up on its own as both a Wi-Fi client and an access point, have it find the camera among its AP clients by name, and store that camera's IP somewhere reusable.

The first useful discovery was that most of that was already built. The repo's rpi_wifi_control/ folder had the tooling, and the Pi already had the units installed:

PieceState before
uap0.service — creates the virtual AP netdevenabled, active
ap-channel-follow.timer — keeps AP channel in syncenabled, active
NM profile rpi-ap (SSID RPi_AP, 192.168.50.1/24, ipv4.method=shared)activated, autoconnect
Station profile A 3 on wlan0connected, autoconnect
Camera discoverymissing
AP actually usable by clientsbroken — 0 stations associated

So the job turned out to be two jobs: find out why a fully-configured AP had no clients, and then build the discovery layer on top of it.

Lesson

Before building anything, inventory what is already there. Half the work here was already done; charging ahead would have produced a duplicate AP stack fighting the existing one — the exact failure mode apsta-doctor.sh check 4 warns about.

2. Working safely on a box with no wired fallback

The very first command run after the connection test was this one, and it shaped everything after:

ip -br addr | grep -v ' lo '
eth0    DOWN
wlan0   UP    192.168.0.110/24
uap0    UP    192.168.50.1/24

eth0 is DOWN. SSH arrives over wlan0 — the same radio that any Wi-Fi change is about to reconfigure. There is no second way in. A botched command means walking to the Pi with a keyboard.

Two habits make that survivable.

Habit 1: run network changes detached

If a command is executed inline over SSH and the SSH session dies halfway through — which is exactly what a Wi-Fi reassociation does — the command dies with it, potentially leaving the interface half-configured. systemd-run hands the work to PID 1, which does not care that your session vanished:

sudo systemd-run --unit=wifi-apply --on-active=2 --collect /bin/bash -c \
  "nmcli con mod 'A 3' 802-11-wireless.band bg; \
   nmcli con up 'A 3'; \
   sleep 10; \
   /usr/local/sbin/ap-channel-follow.sh; \
   logger -t wifi-apply 'band lock applied'"

The --on-active=2 delay lets the SSH command return cleanly before the network moves under it.

Habit 2: arm a rollback before you break anything

Armed first, so it is already ticking when the risky change lands. If the change works, you cancel it. If the Pi drops off the network, nobody cancels it, and in 180 seconds it undoes itself:

sudo systemd-run --unit=wifi-rollback --on-active=180 --collect /bin/bash -c \
  "nmcli con mod 'A 3' 802-11-wireless.band ''; \
   nmcli con up 'A 3'; \
   logger -t wifi-rollback 'band lock REVERTED (nobody cancelled me)'"

# ... apply the change, verify the Pi is healthy, and only then:
sudo systemctl stop wifi-rollback.timer
The general rule

Any remote change that can sever your own connection needs a dead-man's switch. The cost is two extra commands; the alternative is a site visit. This is standard practice for remote router work and applies verbatim to a Pi whose only link is the radio you are editing.

3. Reconnaissance: eight commands that decide everything

No changes were made until these had all been read. Each answers a question that changes what you do next.

CommandQuestion it answers
ip -br addrWhich interface carries my session? Do I have a fallback?
nmcli -t -f NAME,TYPE,DEVICE,AUTOCONNECT con showWhich profiles exist, and will they come back after a reboot?
nmcli -t -f DEVICE,TYPE,STATE,CONNECTION dev statusWhat is actually bound to what right now?
systemctl is-enabled / is-active <unit>Is the automation installed, running, and boot-persistent? (three different things)
iw dev wlan0 info / iw dev uap0 infoWhat channel is each role really on?
iw list | grep -A6 'valid interface combinations'What does this chip physically permit?
sudo iw dev uap0 station dumpIs anything actually associated?
nmcli dev wifi list ifname wlan0What bands/channels does the upstream router offer?
A trap worth remembering

The first run of iw dev uap0 station dump was done without sudo and returned nothing, which looked like "no clients". It was actually a silent permission failure. iw station dumps and scans need root. Also, iw lives in /usr/sbin, which is not on a normal user's PATH — command -v iw reported "missing" while dpkg -l iw showed it installed. Two different ways to be misled by the same tool in one session.

4. The mental model: one radio, one channel

The Pi 4 has a single Wi-Fi chip (brcmfmac). "Concurrent AP+STA" does not mean two radios — it means one radio presenting two virtual netdevs. The chip states its own limits:

iw list | grep -A6 'valid interface combinations'
valid interface combinations:
  * #{ managed } <= 2, ... total <= 3, #channels <= 2
  * #{ managed } <= 1, #{ AP } <= 1, ... total <= 4, #channels <= 1

Read the second line carefully. The combination that allows managed (your station) plus AP permits #channels <= 1. One channel. Total.

The station does not get a vote about this: it joins whatever channel the upstream router put it on, and the AP is dragged along whether its configuration agrees or not.

5. The diagnosis, and the evidence for it

Four observations, each individually unremarkable, that only mean something together:

# 1. The station is on 5 GHz.
iw dev wlan0 info | grep channel
channel 44 (5220 MHz), width: 80 MHz

# 2. The AP netdev has been dragged there with it.
sudo iw dev uap0 info | grep channel
channel 44 (5220 MHz), width: 80 MHz

# 3. But the AP's *profile* still claims 2.4 GHz channel 6 — and says it is fine.
nmcli -g 802-11-wireless.band,802-11-wireless.channel,GENERAL.STATE con show rpi-ap
bg
6
activated

# 4. Nothing is associated.
sudo iw dev uap0 station dump | grep -c Station
0

Then the confirmation, straight from the Pi's own log — the existing ap-channel-follow.sh had been shouting about it every 60 seconds and nobody was reading:

journalctl -t ap-follow -n 3
ap-follow[1892]: wlan0 is on 5 GHz ch 44; the concurrent AP is 2.4 GHz
                 and cannot follow. Pin the upstream to 2.4 GHz or add a USB dongle.

The false lead worth understanding

The first inventory scan reported four devices on the AP — camera, two ESP32s, an iPhone. That looked like a working AP. It was not:

ip neigh show dev uap0
192.168.50.25   INCOMPLETE
192.168.50.246  INCOMPLETE
192.168.50.15   INCOMPLETE

sudo cat /var/lib/NetworkManager/dnsmasq-uap0.leases
1785848540 0c:a6:4c:b7:64:ea 192.168.50.25 H8c_BF9010198_EZVIZ *
                        ^ lease file dated Aug 4 — four days stale

INCOMPLETE means an ARP request went out and nothing answered. Those devices were historical DHCP leases, not present hardware.

This cuts both ways

A DHCP lease outlives the device that took it. That is a hazard — a stale lease can be mistaken for a live device — but it is also a gift: it is how the camera was positively identified (H8c_BF9010198_EZVIZ, MAC 0c:a6:4c:b7:64:ea) while it was switched off and unreachable. Identity from history; presence from ARP. Never confuse the two — which is why the discovery script below records a live flag.

6. The fix: pin the station to 2.4 GHz

Given one shared channel, the two roles must agree. There are three ways out, and the choice is dictated by the hardware:

OptionVerdict
Move the AP up to 5 GHz to match the stationNo. The EZVIZ H8c is 2.4 GHz-only. A 5 GHz AP cannot host the one device this whole system exists to reach.
Add a USB Wi-Fi dongle so the AP gets its own radioCorrect in general, but needs hardware that is not present.
Pull the station down to 2.4 GHzYes — free, reversible, and the upstream supports it.

The third only works if the upstream SSID actually has a 2.4 GHz radio. Verified before touching anything:

sudo nmcli dev wifi rescan ifname wlan0; sleep 6
nmcli -t -f SSID,BSSID,CHAN,FREQ,SIGNAL dev wifi list ifname wlan0 | grep '^A 3:'
A 3:20:23:51:31:43:8D:3:2422 MHz:70    <- 2.4 GHz, channel 3, signal 70
A 3:20:23:51:31:43:8C:44:5220 MHz:55   <- 5 GHz, channel 44, signal 55

Two BSSIDs, one SSID — a dual-band router. And the 2.4 GHz BSS is the stronger of the two (70 vs 55), so the move costs nothing in link quality. NetworkManager had simply preferred 5 GHz on its own.

One property on the station profile does the whole job:

nmcli con mod 'A 3' 802-11-wireless.band bg   # bg = 2.4 GHz; a = 5 GHz
nmcli con up  'A 3'

That is a persistent property of the saved profile, so it survives reboots with no extra unit. Everything downstream then happened without further intervention:

journalctl -t ap-follow -t wifi-apply -n 2
ap-follow[2507]: wlan0 moved to ch 3 (AP had 6) -- resyncing
wifi-apply[2474]: band lock applied

The pre-existing ap-channel-follow.sh noticed the station's new channel, rewrote the AP profile to match, and bounced it. Roughly 75 seconds later the camera reassociated on its own — no camera-side configuration was ever touched. It had been trying to find RPi_AP on 2.4 GHz the whole time.

Result

apsta-doctor.sh went from a channel-mismatch FAIL to "Nothing wrong found on the Pi side."

7. The camera-discovery service

With the AP working, the second half: continuously inventory the AP's clients, pick out the camera by name, and publish its IP somewhere a program can read.

Reuse over reinvention

Your repo already contained the hard part. Rather than writing a new scanner, the existing tools were deployed to the Pi and a thin picker was written on top:

Installed to /usr/local/sbin/Role
ap-clients.shExisting. Joins station dump + DHCP leases + ARP + OUI vendor table into one inventory. --json makes it machine-readable.
onvif-find.pyExisting. Asks cameras their own advertised name over ONVIF WS-Discovery.
apsta-doctor.shExisting. Read-only diagnostic; now on the Pi so it can be run the moment something breaks.
rpi-cam-find.shNew. Calls the above, picks the camera, writes the state files.

Four design decisions worth copying

1 · Rank naming sources by trustworthiness

Cheap cameras lie, or say nothing at all. The picker tries five fields in a fixed order and stops at the first hit, so a hand-set alias always beats a guessed vendor string:

FIELDS = ("alias", "onvif", "dhcp_name", "name", "vendor")
#          ^you set it   ^camera says it   ^camera asked for it   ^OUI guess

Here the match landed on dhcp_name = "H8c_BF9010198_EZVIZ" against the configured pattern H8c.

2 · Identify once, then track by MAC

Names are unreliable over time: ONVIF gets skipped on cheap runs, DHCP hostnames expire. A MAC does not change. So if no name matches this round but the previously-identified MAC is still on the AP, the script carries the identification forward and just updates the IP:

if best is None:
    prev = json.load(open(cam_json))          # what we decided last time
    for d in devs:
        if d["mac"].lower() == prev["mac"].lower() and d.get("ip"):
            best = (99, d, "carried-forward", prev.get("matched_value", ""))

Without this, a scan that skipped ONVIF would "lose" a camera that never left.

3 · Record presence separately from identity

This is the stale-lease hazard from section 5, handled explicitly. flags == 0x0 in /proc/net/arp means the entry is incomplete — nothing answered:

for line in open("/proc/net/arp").readlines()[1:]:
    f = line.split()
    if len(f) >= 4 and f[0] == d["ip"] and f[2] != "0x0":
        live = True

Consumers get CAMERA_LIVE=1 or 0 and can decide whether a remembered address is good enough for what they are about to do.

4 · Make the expensive path optional

ONVIF discovery waits ~5 s for UDP replies. Doing that every 60 s forever is wasteful once the answer is known, so it is skipped whenever the camera's MAC is already in the ARP table:

if [ -n "$prev_mac" ] && ip neigh show dev "$AP_IFACE" | grep -qi -- "$prev_mac"; then
    USE_ONVIF=0
fi

Where the answer ends up

Four outputs, because different consumers want different shapes:

. /var/lib/rpi-ap-sta/camera.env   # shell: CAMERA_IP, CAMERA_MAC, CAMERA_RTSP, CAMERA_LIVE
cat /var/lib/rpi-ap-sta/camera.json # full record incl. why it matched
cat /run/rpi-camera-ip              # just the IP, one line
ping ipcam                          # /etc/hosts alias, kept current

cat /var/lib/rpi-ap-sta/ap-clients.json # every device seen on the AP

The /etc/hosts line is maintained with a sentinel comment and rewritten via cat > rather than mv, so the file keeps its inode and permissions:

tmp=$(mktemp)
grep -v '# rpi-cam-find$' /etc/hosts > "$tmp"
printf '%s\t%s\t# rpi-cam-find\n' "$ip" "$CAM_ALIAS" >> "$tmp"
cat "$tmp" > /etc/hosts    # NOT mv — preserves inode and mode

Scheduling, and one systemd subtlety

# /etc/systemd/system/rpi-cam-find.timer
OnBootSec=45s        # uap0 exists, DHCP has had a chance to hand out a lease
OnUnitActiveSec=60s

# /etc/systemd/system/rpi-cam-find.service
Type=oneshot
SuccessExitStatus=3
Why SuccessExitStatus=3 matters

The script exits 3 for "AP is healthy, the camera just is not connected yet". That is a completely normal state — the camera may be powered off. Without this line systemd would mark the unit failed every minute, filling the journal with noise and burying real failures. Give your "nothing to do" case its own exit code and tell systemd it is a success.

8. Making it survive a reboot, and proving it did

"Enabled", "active", and "will work after a reboot" are three different claims. Checked all of them before rebooting:

for u in uap0.service ap-channel-follow.timer rpi-cam-find.timer NetworkManager; do
    printf '%-28s %s\n' "$u" "$(systemctl is-enabled $u)"
done
uap0.service                 enabled
ap-channel-follow.timer      enabled
rpi-cam-find.timer           enabled
NetworkManager               enabled

nmcli -g connection.autoconnect,802-11-wireless.band con show 'A 3'
yes
bg
A mistake this catches

systemctl enable arranges for a unit to start at next boot; it does not start it now. Right after enabling, rpi-cam-find.timer read enabled / inactive — it would have worked after the reboot but was doing nothing in the meantime. enable --now, or an explicit start, closes that gap.

Then the real test — a reboot, which is the only honest proof that nothing depended on a shell that has since exited:

sudo systemd-run --on-active=3 --collect /sbin/reboot

Post-reboot, at 1 minute uptime, with nothing typed in between:

10. Adapting it

Different camera, or a second one

Edit CAM_PATTERN in /etc/default/rpi-ap-camera (* is a wildcard, e.g. H8c-*), then sudo systemctl restart rpi-cam-find.service. If the device advertises no usable name, identify it by power-cycling and label it permanently:

sudo bash /usr/local/sbin/ap-clients.sh --find              # unplug it, watch what leaves
sudo bash /usr/local/sbin/ap-clients.sh --alias 192.168.50.25 gate-cam

Pin the camera to a fixed IP

Not done here — the current design records whatever DHCP gives. To pin it, now that the MAC is known:

sudo mkdir -p /etc/NetworkManager/dnsmasq-shared.d
echo 'dhcp-host=0c:a6:4c:b7:64:ea,192.168.50.90,ipcam' \
  | sudo tee /etc/NetworkManager/dnsmasq-shared.d/ipcam.conf
sudo nmcli con down rpi-ap && sudo nmcli con up rpi-ap

Keep 5 GHz upstream

The only real answer is a second radio: a USB Wi-Fi dongle for uap0, leaving the built-in chip free for 5 GHz. Then #channels <= 1 no longer binds, because there are two radios.

Standing risk in this deployment

A 3 is now locked to band bg. If that router's 2.4 GHz radio is ever turned off or renamed, the Pi will not reconnect — and with eth0 DOWN there is no other way in. If the Pi is hard to reach physically, bring eth0 up as a standing safety net.
