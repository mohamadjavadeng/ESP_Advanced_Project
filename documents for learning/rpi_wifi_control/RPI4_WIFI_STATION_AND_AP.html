Raspberry Pi 4 — Wi-Fi station and access point at the same time

One built-in radio, both roles, brought up automatically on every boot. wlan0 stays a client on your normal Wi-Fi; a second virtual interface uap0 runs a WPA2 access point at a fixed 192.168.50.1 that your ESP32s join. Copy-paste one script and reboot.

1Read this first

Everything below reconfigures Wi-Fi on the machine you are probably SSH'd into. The design deliberately never touches wlan0, so your session should survive — but iw, rfkill and NetworkManager restarts can still drop a link.

Have a way back in. Do the first install over Ethernet, or with a keyboard and monitor on the Pi, or at least know how to pull the SD card. If you lose the network, the uninstall block is two commands from a local console.
┌──────────────── Raspberry Pi 4 ───────────────┐ │ ONE physical radio (brcmfmac, 2.4/5 GHz) │ router / phone │ │ ────────wifi─────┼──▶ wlan0 STATION ── internet, cloud, apt │ │ │ │ │ └── same chip ⇒ ONE CHANNEL for both │ │ │ ESP32 STICK ─────┼──▶ uap0 ACCESS POINT 192.168.50.1 │ ESP32 BEAM ─────┼──▶ WPA2 · DHCP · NAT to wlan0 │ laptop ─────┼──▶ │ │ │ │ a server bound to 0.0.0.0 is reachable │ │ on BOTH interfaces at once │ └───────────────────────────────────────────────┘

2Can the Pi 4 radio actually do it?

"Is simultaneous station + AP possible, or do I need a second adapter?"

Possible, no extra hardware. The Broadcom chip supports one station link plus one AP concurrently. What you cannot do is expose both through a single interface name — so you add a second virtual netdev on the same PHY. Ask the driver yourself rather than trusting a blog post:

iw list | grep -A 8 'valid interface combinations'

On a Pi 4 you get something like this — the second bullet is the one that matters:

valid interface combinations:
     * #{ managed } <= 1, #{ P2P-device } <= 1, #{ P2P-client, P2P-GO } <= 1,
       total <= 3, #channels <= 2
     * #{ managed } <= 1, #{ AP } <= 1, #{ P2P-client } <= 1, #{ P2P-device } <= 1,
       total <= 4, #channels <= 1

#{ managed } <= 1, #{ AP } <= 1 is the permission slip: one station, one AP, together. #channels <= 1 is the price.

The one hard limit: both roles share a single channel. Whatever channel wlan0 associates on, the AP is forced onto. If wlan0 later joins a router on a different channel, the AP's advertised channel goes stale and clients silently stop associating. Section 6 is the fix, and it is not optional on a machine that meets a new modem every week.

3Route A — NetworkManagerrecommended

Raspberry Pi OS Bookworm and Trixie manage Wi-Fi with NetworkManager. Let it run the AP too: an ipv4.method=shared profile gives you a fixed address, a DHCP server and NAT out through wlan0 for free — no hostapd, no dnsmasq config, no iptables rules to maintain. Devices on the AP get real internet.

Check you are on this route (running ⇒ yes; if the command is missing, use Route B):

systemctl is-active NetworkManager && nmcli --version
Migrating from this repo's ap_sta_setup.py? That script is the Route B (hostapd + dnsmasq) design, and two of its leftovers make Route A fail outright: its hostapd/dnsmasq daemons still holding uap0, and /etc/NetworkManager/conf.d/unmanaged-uap0.conf, which tells NetworkManager to ignore the very interface the new profile needs. Step 2 below clears both. Your SSID, password and 192.168.50.1 stay the same, so the ESP32 firmware needs no edits.

Step 1 — Confirm you are on this route

Route A needs NetworkManager. Bookworm and Trixie have it; older Lite images may not.

systemctl is-active NetworkManager        # want: active
nmcli --version                           # want: 1.42 or newer
grep VERSION_CODENAME /etc/os-release     # bookworm / trixie

inactive or nmcli: command not found ⇒ stop here and use Route B instead.

Step 2 — Clear any previous hostapd install

Skip only if this Pi has never run ap_sta_setup.py or a hostapd hotspot guide. The unmanaged-uap0.conf line is the one that silently breaks everything later with "No suitable device found".

sudo systemctl disable --now hostapd dnsmasq ap-sta 2>/dev/null
sudo rm -f /etc/NetworkManager/conf.d/unmanaged-uap0.conf \
           /etc/systemd/system/hostapd.service.d/override.conf \
           /etc/systemd/system/dnsmasq.service.d/override.conf \
           /etc/dnsmasq.d/uap0.conf
sudo sed -i '/^denyinterfaces uap0/d' /etc/dhcpcd.conf 2>/dev/null
sudo systemctl daemon-reload
sudo systemctl reload NetworkManager

# nothing should be left holding the AP or port 53
systemctl is-enabled hostapd dnsmasq 2>/dev/null      # want: disabled / not-found

The dnsmasq package can stay installed — only its service must be off, because NetworkManager runs its own instance.

Step 3 — Ask the radio if it can do both

Do this before building anything on top of it. You want a combination line naming both managed and AP.

iw list | grep -A 8 'valid interface combinations'
     * #{ managed } <= 1, #{ AP } <= 1, #{ P2P-client } <= 1, #{ P2P-device } <= 1,
       total <= 4, #channels <= 1          <-- this line is your permission slip

No such line ⇒ this radio cannot do concurrency at all; go to Route C. #channels <= 1 is why steps 11 and 15 exist.

Step 4 — Install packages

dnsmasq-base, not dnsmasq. NetworkManager spawns its own instance for ipv4.method=shared; the full package adds a second daemon that binds :53 and fights it.

sudo apt update
sudo apt install -y iw rfkill dnsmasq-base
dpkg -s dnsmasq-base | grep ^Status        # want: install ok installed

Step 5 — Set the regulatory domain

An unset country leaves the reg domain at 00 / DFS-UNSET, and the AP either refuses to start or comes up at minimum power. Use your own two-letter code.

sudo raspi-config nonint do_wifi_country US     # GB DE OM AE IR ...
sudo rfkill unblock wlan

iw reg get | head -3                            # must NOT say 'country 00: DFS-UNSET'
rfkill list wlan                                # both blocks: no

Step 6 — Get wlan0 onto your Wi-Fi

The station link must already work; the AP is added alongside it and never replaces it. Also kill power save here — it costs seconds of latency on ESP32 POSTs.

nmcli dev wifi list ifname wlan0
sudo nmcli dev wifi connect "YOUR_SSID" password "YOUR_PASSWORD" ifname wlan0

iw dev wlan0 link                               # Connected to ..., channel N
nmcli -g GENERAL.CONNECTION,IP4.ADDRESS dev show wlan0

# turn off power save on whatever profile wlan0 just used
STA=$(nmcli -g GENERAL.CONNECTION dev show wlan0 | head -1)
sudo nmcli connection modify "$STA" 802-11-wireless.powersave 2
sudo nmcli connection up "$STA"
2.4 GHz upstream, please. If iw dev wlan0 link reports a channel above 14, the station is on 5 GHz and a concurrent 2.4 GHz AP has no channel to share with it. Force the router or phone hotspot to 2.4 GHz now, or accept Route C.

Step 7 — Write the shared settings file

Both scripts source this, so the interface names live in exactly one place.

sudo tee /etc/default/rpi-ap-sta >/dev/null <<'EOF'
# Shared by uap0-up.sh and ap-channel-follow.sh.
STA_IFACE=wlan0
AP_IFACE=uap0
AP_TYPE=__ap
AP_CON=rpi-ap
EOF
cat /etc/default/rpi-ap-sta

Step 8 — Write the interface-creation script

This is the actual concurrency trick: a second virtual netdev on the same PHY, given a different MAC.

sudo tee /usr/local/sbin/uap0-up.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# Add a second virtual netdev on the SAME physical radio as the station, so one
# chip can be a client and an access point at once. Idempotent.
#
# Ordered BEFORE NetworkManager on purpose: brcmfmac frequently returns
# EBUSY (-16) when asked to add an interface while wlan0 is already associated.
set -euo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
. /etc/default/rpi-ap-sta

rfkill unblock wlan || true

# systemd .device units can lose the race against module load at boot, so wait
# for the radio here rather than trusting the ordering alone.
for _ in $(seq 1 30); do
    [[ -d /sys/class/net/$STA_IFACE ]] && break
    sleep 1
done
[[ -d /sys/class/net/$STA_IFACE ]] || { echo "$STA_IFACE never appeared" >&2; exit 1; }

iw dev | grep -qw "$AP_IFACE" \
    || iw dev "$STA_IFACE" interface add "$AP_IFACE" type "$AP_TYPE"

# Both netdevs inherit the one MAC of the one chip. Flip the locally-administered
# bit so the AP and the station are distinct L2 endpoints -- sharing a MAC breaks
# ARP and DHCP for anything that joins the AP.
mac=$(cat "/sys/class/net/$STA_IFACE/address")
want="$(printf '%02x' $(( 0x${mac:0:2} ^ 0x02 )))${mac:2}"
if [[ "$(cat /sys/class/net/$AP_IFACE/address)" != "$want" ]]; then
    ip link set dev "$AP_IFACE" down
    ip link set dev "$AP_IFACE" address "$want"
fi
ip link set dev "$AP_IFACE" up
EOF
sudo chmod 755 /usr/local/sbin/uap0-up.sh
sudo bash -n /usr/local/sbin/uap0-up.sh      # syntax check, changes nothing

Step 9 — Write the startup unit

This is the "command in startup code" you asked about. The two lines that matter are ExecStart and Before=NetworkManager.service — the ordering is what makes it survive cold boots instead of only working when you type it by hand.

sudo tee /etc/systemd/system/uap0.service >/dev/null <<'EOF'
[Unit]
Description=Create uap0 virtual AP interface on the wlan0 radio
Wants=sys-subsystem-net-devices-wlan0.device
After=sys-subsystem-net-devices-wlan0.device
Before=NetworkManager.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/uap0-up.sh
ExecStop=-/usr/sbin/iw dev uap0 del

[Install]
WantedBy=multi-user.target
EOF
sudo systemd-analyze verify /etc/systemd/system/uap0.service   # silence = valid

Do not use crontab @reboot for this. Cron starts after NetworkManager, which is the one ordering that reliably fails with EBUSY (-16).

Step 10 — Enable it, and create uap0 now

sudo systemctl daemon-reload
sudo systemctl enable uap0.service
sudo systemctl start uap0.service

iw dev                              # uap0 listed, 'type AP', same phy#0 as wlan0
ip -br link show uap0 wlan0         # the two MACs MUST differ (bit flipped)
systemctl status uap0 --no-pager
If start fails with Device or resource busy (-16): that is expected — the radio is busy with your live association. Nothing is broken and the unit is already enabled, so it will run at boot when the radio is idle. Finish steps 11–16, then sudo reboot and re-check.

Step 11 — Read the station's channel

One radio, one channel. Capture it into a variable and keep the same shell for steps 12–14.

CHAN=$(iw dev wlan0 info | awk '$1=="channel"{print $2}')
CHAN=${CHAN:-6}                                  # fallback if wlan0 is not associated
[ "$CHAN" -gt 14 ] && { echo "wlan0 is on 5 GHz ch $CHAN -- AP falls back to 6"; CHAN=6; }
echo "AP channel = $CHAN"

Step 12 — Create the AP profile

Bind it to uap0, never to wlan0.

sudo nmcli connection delete rpi-ap 2>/dev/null      # ignore 'unknown connection'
sudo nmcli connection add type wifi ifname uap0 con-name rpi-ap \
     autoconnect yes ssid RPi_AP
Never use nmcli device wifi hotspot here. It reconfigures wlan0 itself and drops your station link — and with it your SSH session. The whole point of uap0 is to avoid that command.

Step 13 — Configure the AP profile

One command. Put your real password in wifi-sec.psk (8–63 characters).

sudo nmcli connection modify rpi-ap \
     802-11-wireless.mode ap \
     802-11-wireless.band bg \
     802-11-wireless.channel "$CHAN" \
     802-11-wireless.powersave 2 \
     wifi-sec.key-mgmt wpa-psk \
     wifi-sec.proto rsn \
     wifi-sec.pairwise ccmp \
     wifi-sec.group ccmp \
     wifi-sec.psk 'raspberry123' \
     ipv4.method shared \
     ipv4.addresses 192.168.50.1/24 \
     ipv6.method disabled \
     connection.autoconnect-priority 10 \
     connection.autoconnect-retries 0
PropertyValueWhy
802-11-wireless.modeapMakes this an access point instead of a client. The single most important line
.band · .channelbg · $CHAN2.4 GHz, pinned to the station's channel. One radio cannot hold two
.powersave2 (disable)An AP that sleeps adds latency and drops associations
wifi-sec.key-mgmtwpa-pskPre-shared key
.proto · .pairwise · .grouprsn · ccmp · ccmpWPA2-CCMP only. Explicitly excludes WPA1 and TKIP, which some ESP32 stacks will happily negotiate down to
wifi-sec.pskyour password8–63 characters, or the profile is rejected
ipv4.methodsharedDoes three jobs: static address, DHCP server for AP clients, and NAT out via the default route. This is why Route A needs no dnsmasq config and no iptables rules
ipv4.addresses192.168.50.1/24The fixed address your ESP32s hard-code. Defines the DHCP subnet too
ipv6.methoddisabledNothing on this AP needs it; avoids router-advertisement noise
connection.autoconnect-priority10Comes up ahead of other profiles at boot
connection.autoconnect-retries0Retry forever. The default gives up after 4 attempts — fatal if uap0 appears a moment late

Step 14 — Activate the AP

sudo nmcli connection up rpi-ap

nmcli -f GENERAL.STATE,IP4.ADDRESS connection show rpi-ap   # activated · 192.168.50.1/24
nmcli -g ipv4.method connection show rpi-ap                 # shared
iw dev uap0 info | grep -E 'type|channel|ssid'
iw dev wlan0 link | head -2                                 # station still up

Now join RPi_AP from a phone. You should get a 192.168.50.x address and working internet — that is ipv4.method=shared doing DHCP and NAT for you.

Step 15 — Write the channel follower

Without this, the day wlan0 joins a router on a different channel your AP keeps beaconing a stale one and the ESP32s silently stop associating. Nothing logs an error. This is the failure that wastes days in the field.

sudo tee /usr/local/sbin/ap-channel-follow.sh >/dev/null <<'EOF'
#!/usr/bin/env bash
# One radio cannot hold two channels (see: iw list -> '#channels <= 1'). When the
# station joins a router on a different channel, the AP profile's channel goes
# stale and clients silently stop associating. Re-sync and reactivate.
set -uo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
. /etc/default/rpi-ap-sta

cur=$(iw dev "$STA_IFACE" info 2>/dev/null | awk '$1=="channel"{print $2}')
[ -z "${cur:-}" ] && exit 0                    # not associated: nothing to follow

if [ "$cur" -gt 14 ]; then
    logger -t ap-follow "$STA_IFACE is on 5 GHz ch $cur; the concurrent AP is 2.4 GHz and cannot follow. Pin the upstream to 2.4 GHz or add a USB dongle."
    exit 0
fi

want=$(nmcli -g 802-11-wireless.channel connection show "$AP_CON")
[ "$cur" = "$want" ] && exit 0                 # in sync: cheap no-op

logger -t ap-follow "$STA_IFACE moved to ch $cur (AP had ${want:-unset}) -- resyncing"
nmcli connection modify "$AP_CON" 802-11-wireless.band bg 802-11-wireless.channel "$cur"
nmcli connection up "$AP_CON"
EOF
sudo chmod 755 /usr/local/sbin/ap-channel-follow.sh

sudo /usr/local/sbin/ap-channel-follow.sh      # run once by hand
journalctl -t ap-follow -n 10 --no-pager       # silent = already in sync

Step 16 — Schedule the follower

A timer, not a cron job, so it inherits systemd ordering and logs to the journal.

sudo tee /etc/systemd/system/ap-channel-follow.service >/dev/null <<'EOF'
[Unit]
Description=Re-sync the AP channel to the station channel
After=NetworkManager.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/ap-channel-follow.sh
EOF

sudo tee /etc/systemd/system/ap-channel-follow.timer >/dev/null <<'EOF'
[Unit]
Description=Check every minute whether the station changed channel

[Timer]
OnBootSec=90
OnUnitActiveSec=60

[Install]
WantedBy=timers.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now ap-channel-follow.timer
systemctl list-timers ap-channel-follow.timer --no-pager    # confirm it is scheduled

Step 17 — Verify

# one PHY, two netdevs, one of them type AP
iw dev

# distinct MACs, AP has the fixed address
ip -br link show wlan0 uap0
ip -br addr show uap0

# NetworkManager state
nmcli -f GENERAL.STATE,IP4.ADDRESS connection show rpi-ap
nmcli device status

# both roles on the same channel -- these two numbers must match
iw dev wlan0 info | grep channel
iw dev uap0  info | grep channel

# station link untouched, and internet still works through it
iw dev wlan0 link
ping -c2 -I wlan0 1.1.1.1

# everything enabled for next boot
systemctl is-enabled uap0.service ap-channel-follow.timer

Step 18 — Reboot and prove it comes back

Unattended bring-up is the whole point. An install that only works until the next power cut is not finished.

sudo reboot

# after it comes back:
iw dev | grep -A3 uap0
nmcli -f GENERAL.STATE connection show rpi-ap        # activated
systemctl status uap0 --no-pager
journalctl -u uap0 -t ap-follow -b --no-pager        # clean boot, no EBUSY

# and from a client on the AP:
sudo iw dev uap0 station dump | grep -E 'Station|signal:'
cat /var/lib/NetworkManager/dnsmasq-uap0.leases
Done. wlan0 is a station on your Wi-Fi, uap0 is a WPA2 AP at 192.168.50.1 handing out DHCP and NAT, both on one radio, and both return on every boot without you touching anything.

Or: one script that runs all eighteen steps

Same result, one paste. Edit the settings at the top first. Idempotent — re-run it after changing the SSID or password.

rpi4-ap-sta.sh  ·  sudo bash rpi4-ap-sta.sh 
#!/usr/bin/env bash
# Raspberry Pi 4: Wi-Fi STATION and ACCESS POINT at the same time, on the single
# built-in radio, brought up automatically on every boot.
#
#   wlan0  station -> joins your normal Wi-Fi / phone hotspot, keeps internet
#   uap0   AP      -> fixed 192.168.50.1, WPA2; NetworkManager does DHCP + NAT
#
# Run once:  sudo bash rpi4-ap-sta.sh
# Then:      sudo reboot          # proves it comes back unattended

set -euo pipefail

# ---------------------------- settings -------------------------------------- #
AP_SSID="RPi_AP"
AP_PASS="raspberry123"          # 8..63 characters
AP_ADDR="192.168.50.1/24"       # the Pi's fixed address on its own AP
COUNTRY="US"                    # your regulatory domain: GB DE OM IR AE ...
AP_CON="rpi-ap"                 # NetworkManager profile name
AP_IFACE="uap0"                 # virtual AP interface we create
STA_IFACE="wlan0"               # the physical radio, stays the station
AP_TYPE="__ap"                  # if NM refuses to activate, retry with: managed
# ---------------------------------------------------------------------------- #

[[ $EUID -eq 0 ]] || { echo "run me with sudo" >&2; exit 1; }
(( ${#AP_PASS} >= 8 )) || { echo "AP_PASS needs 8+ characters for WPA2" >&2; exit 1; }
command -v nmcli >/dev/null || { echo "no nmcli -- use Route B (hostapd) instead" >&2; exit 1; }

echo "== 0/6  stand down any previous hostapd-style (Route B) install =="
# If this Pi already ran raspberry_pi/ap_sta_setup.py, two leftovers will break
# Route A outright, so clear them rather than debugging them later:
#   * hostapd/dnsmasq daemons still owning uap0 and :53
#   * an NM conf.d rule marking uap0 unmanaged -> "No suitable device found"
for svc in hostapd dnsmasq ap-sta; do
    if systemctl is-enabled --quiet "$svc" 2>/dev/null || systemctl is-active --quiet "$svc" 2>/dev/null; then
        echo "  disabling $svc (was a Route B component)"
        systemctl disable --now "$svc" >/dev/null 2>&1 || true
    fi
done
for f in /etc/NetworkManager/conf.d/unmanaged-uap0.conf \
         /etc/systemd/system/hostapd.service.d/override.conf \
         /etc/systemd/system/dnsmasq.service.d/override.conf \
         /etc/dnsmasq.d/uap0.conf; do
    [[ -e $f ]] && { echo "  removing $f"; rm -f "$f"; }
done
grep -q '^denyinterfaces uap0' /etc/dhcpcd.conf 2>/dev/null \
    && sed -i '/^denyinterfaces uap0/d' /etc/dhcpcd.conf
systemctl daemon-reload
systemctl reload NetworkManager 2>/dev/null || true

echo "== 1/6  packages =="
# dnsmasq-base, NOT dnsmasq. NetworkManager spawns its own instance for
# ipv4.method=shared; the full dnsmasq package adds a SECOND daemon that binds
# :53 and fights it. If the full package is installed, leaving its service
# disabled (step 0) is enough -- no need to uninstall it.
apt-get update -qq
apt-get install -y -qq iw rfkill dnsmasq-base

echo "== 2/6  what the radio admits it can do =="
# Want a combination line with both '#{ managed }' and '#{ AP }'.
# '#channels <= 1' on that line is the shared-channel limit -- see the follower below.
iw list | grep -A 8 'valid interface combinations' || true

echo "== 3/6  regulatory domain + radio unblock =="
# An unset country leaves the reg domain at 00/DFS-UNSET and the AP either refuses
# to start or comes up at minimum power.
raspi-config nonint do_wifi_country "$COUNTRY" 2>/dev/null || iw reg set "$COUNTRY"
rfkill unblock wlan

echo "== 4/6  settings + boot-time creation of $AP_IFACE =="
cat > /etc/default/rpi-ap-sta <<EOF

STA_IFACE=$STA_IFACE
AP_IFACE=$AP_IFACE
AP_TYPE=$AP_TYPE
AP_CON=$AP_CON
EOF

      802-11-wireless.mode ap \
      802-11-wireless.band bg \
      802-11-wireless.channel "$CHAN" \
      802-11-wireless.powersave 2 \
      wifi-sec.key-mgmt wpa-psk \
      wifi-sec.proto rsn \
      wifi-sec.pairwise ccmp \
      wifi-sec.group ccmp \
      wifi-sec.psk "$AP_PASS" \
      ipv4.method shared \
      ipv4.addresses "$AP_ADDR" \
      ipv6.method disabled \
      connection.autoconnect-priority 10 \
      connection.autoconnect-retries 0
# ipv4.method=shared is doing three jobs: the static address above, a DHCP server
# for AP clients, and NAT/masquerade out via the default route (wlan0). That is
# why this route needs no dnsmasq.conf and no iptables lines of your own.

echo "== 6/6  channel follower + enable everything =="
cat > /usr/local/sbin/ap-channel-follow.sh <<'EOF'
#!/usr/bin/env bash
# One radio cannot hold two channels (see: iw list -> '#channels <= 1'). When the
# station joins a router on a different channel, the AP profile's channel goes
# stale and clients silently stop associating. Re-sync and reactivate.
set -uo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
. /etc/default/rpi-ap-sta

cur=$(iw dev "$STA_IFACE" info 2>/dev/null | awk '$1=="channel"{print $2}')
[ -z "${cur:-}" ] && exit 0                    # not associated: nothing to follow

if [ "$cur" -gt 14 ]; then
    logger -t ap-follow "$STA_IFACE is on 5 GHz ch $cur; the concurrent AP is 2.4 GHz and cannot follow. Pin the upstream to 2.4 GHz or add a USB dongle."
    exit 0
fi

want=$(nmcli -g 802-11-wireless.channel connection show "$AP_CON")
[ "$cur" = "$want" ] && exit 0                 # in sync: cheap no-op

logger -t ap-follow "$STA_IFACE moved to ch $cur (AP had ${want:-unset}) -- resyncing"
nmcli connection modify "$AP_CON" 802-11-wireless.band bg 802-11-wireless.channel "$cur"
nmcli connection up "$AP_CON"
EOF
chmod 755 /usr/local/sbin/ap-channel-follow.sh

cat > /etc/systemd/system/ap-channel-follow.service <<'EOF'
[Unit]
Description=Re-sync the AP channel to the station channel
After=NetworkManager.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/ap-channel-follow.sh
EOF

cat > /etc/systemd/system/ap-channel-follow.timer <<'EOF'
[Unit]
Description=Check every minute whether the station changed channel

[Timer]
OnBootSec=90
OnUnitActiveSec=60

[Install]
WantedBy=timers.target
EOF

systemctl daemon-reload
systemctl enable uap0.service ap-channel-follow.timer >/dev/null
systemctl start ap-channel-follow.timer

if systemctl start uap0.service; then
    nmcli connection up "$AP_CON" || echo "  (!) profile did not activate -- see Troubleshooting"
else
    echo "  (!) could not create $AP_IFACE right now: the radio is busy with an"
    echo "      active association. It IS enabled at boot, where the unit runs"
    echo "      before NetworkManager. Just reboot:  sudo reboot"
fi

cat <<SUMMARY

================================================================
Concurrent Wi-Fi station + access point installed.
  AP SSID    : $AP_SSID
  AP password: $AP_PASS
  Pi AP IP   : ${AP_ADDR%%/*}   (fixed)
  DHCP + NAT : NetworkManager (ipv4.method=shared)
  AP channel : $CHAN            (must match $STA_IFACE)
  Station    : $STA_IFACE, untouched -- still your internet path

Verify:
  iw dev                                  # $AP_IFACE listed, type AP
  ip -br addr show $AP_IFACE              # ${AP_ADDR%%/*}
  nmcli -f GENERAL.STATE con show $AP_CON # activated
  iw dev $STA_IFACE link                  # still associated as a client
  sudo iw dev $AP_IFACE station dump      # who joined the AP

Reboot to confirm unattended bring-up:  sudo reboot
================================================================
SUMMARY
Answering your "a command in startup code" question directly: yes — and the startup command is exactly the two lines inside uap0.service. Everything else in that installer is settings and safety. The minimum viable startup command is iw dev wlan0 interface add uap0 type __ap; the script adds a wait loop, a distinct MAC, and correct ordering, which is the difference between "works when I type it" and "works after every cold boot in the field".

A crontab @reboot line would also fire it, but cron starts after NetworkManager, which is the one ordering that reliably fails with EBUSY. Use the systemd unit.

6Keep the AP on the station's channel

This is the failure that wastes days, so it is worth stating plainly: the AP does not break loudly. It keeps beaconing on a channel the radio is no longer really on, and the ESP32s just stop associating. Nothing logs an error.

The installer already deployed and enabled the follower. Confirm and watch it:

systemctl list-timers ap-channel-follow.timer     # scheduled?
sudo /usr/local/sbin/ap-channel-follow.sh         # run it by hand, once
journalctl -t ap-follow -f                        # watch it resync

Trigger it deliberately: move the Pi to a router on another channel, or retune your phone hotspot, then watch journalctl -t ap-follow log wlan0 moved to ch N … resyncing.

The follower cannot rescue a 5 GHz upstream. If wlan0 joins on channel 36 or above, a concurrent 2.4 GHz AP has nowhere to follow to. The script logs that and gives up rather than writing an invalid profile. Fix it upstream: force the router or hotspot to 2.4 GHz, or go to Route C.

7Route B — hostapd + dnsmasqno NetworkManager

Use this on Bullseye, on Lite images still using dhcpcd, or anywhere you want the AP fully independent of NetworkManager. Same uap0 trick; you supply the AP daemon and DHCP server yourself. This repo already ships a scripted version of exactly this at raspberry_pi/ap_sta_setup.py — the blocks below are the same thing by hand, plus the NAT that script omits.

sudo apt install -y hostapd dnsmasq iw rfkill
sudo systemctl unmask hostapd          # Raspberry Pi OS ships it masked
/etc/hostapd/hostapd.conf 
# Access point on the virtual interface, concurrent with the wlan0 station.
country_code=US
interface=uap0
driver=nl80211
ssid=RPi_AP
hw_mode=g
channel=6                  # MUST equal `iw dev wlan0 info | grep channel`
ieee80211n=1
wmm_enabled=1
macaddr_acl=0
auth_algs=1
ignore_broadcast_ssid=0
wpa=2
wpa_passphrase=raspberry123
wpa_key_mgmt=WPA-PSK
rsn_pairwise=CCMP
/etc/dnsmasq.d/uap0.conf 
# DHCP for the AP only.
# port=0 disables dnsmasq's DNS server so it cannot fight systemd-resolved on :53.
# bind-dynamic tolerates uap0 appearing after dnsmasq has started.
interface=uap0
bind-dynamic
port=0
dhcp-range=192.168.50.10,192.168.50.100,255.255.255.0,24h
dhcp-option=uap0,3,192.168.50.1        # default gateway = the Pi
dhcp-option=uap0,6,1.1.1.1,8.8.8.8     # DNS, since we disabled our own

Reuse uap0-up.sh and uap0.service from Route A verbatim, but add the address there (Route A let NetworkManager do it) and drop the Before=NetworkManager.service line if NM is absent:

# append to /usr/local/sbin/uap0-up.sh
ip addr flush dev "$AP_IFACE"
ip addr add 192.168.50.1/24 dev "$AP_IFACE"

Stop the network manager from stealing uap0 back — one of these, whichever you run:

# NetworkManager present but you want hostapd to own the AP:
printf '[keyfile]\nunmanaged-devices=interface-name:uap0\n' \
  | sudo tee /etc/NetworkManager/conf.d/unmanaged-uap0.conf
sudo systemctl reload NetworkManager

# dhcpcd instead:
printf '\n# concurrent AP+STA: uap0.service owns this interface\ndenyinterfaces uap0\n' \
  | sudo tee -a /etc/dhcpcd.conf

Order the daemons after the interface exists, then enable:

for u in hostapd dnsmasq; do
  sudo mkdir -p /etc/systemd/system/$u.service.d
  printf '[Unit]\nAfter=uap0.service\nRequires=uap0.service\n' \
    | sudo tee /etc/systemd/system/$u.service.d/override.conf
done
sudo systemctl daemon-reload
sudo systemctl enable --now uap0 hostapd dnsmasq

NAT — give AP clients internet (Route A does this for you; here you must)

# persistent kernel forwarding
printf 'net.ipv4.ip_forward=1\n' | sudo tee /etc/sysctl.d/99-ap-sta-forward.conf
sudo sysctl --system

# masquerade AP traffic out through the station interface, and persist it
sudo apt install -y iptables-persistent      # answer "yes" to saving current rules
sudo iptables -t nat -A POSTROUTING -o wlan0 -j MASQUERADE
sudo iptables -A FORWARD -i uap0 -o wlan0 -j ACCEPT
sudo iptables -A FORWARD -i wlan0 -o uap0 -m state --state RELATED,ESTABLISHED -j ACCEPT
sudo netfilter-persistent save

The channel follower for this route edits the config file instead of an NM profile:

#!/usr/bin/env bash
# /usr/local/sbin/ap-channel-follow.sh  (hostapd variant)
set -uo pipefail
PATH=/usr/sbin:/usr/bin:/sbin:/bin
CONF=/etc/hostapd/hostapd.conf

cur=$(iw dev wlan0 info | awk '$1=="channel"{print $2}')
[ -z "${cur:-}" ] && exit 0
[ "$cur" -gt 14 ] && { logger -t ap-follow "wlan0 on 5 GHz ch $cur; 2.4 GHz AP cannot follow"; exit 0; }

want=$(awk -F= '$1=="channel"{print $2}' "$CONF")
[ "$cur" = "$want" ] && exit 0

logger -t ap-follow "wlan0 moved to ch $cur (hostapd had $want) -- resyncing"
sed -i "s/^channel=.*/channel=$cur/" "$CONF"
systemctl restart hostapd

8Route C — USB dongletwo radios

A ~$10 USB Wi-Fi adapter deletes the entire shared-channel problem: run the AP on one radio and the station on the other, on independent channels, and throw the follower away. If the Pi is going somewhere you cannot easily reach, buy the dongle.

# confirm the dongle can do AP mode at all before relying on it
iw list | grep -A 12 'Supported interface modes'      # need '* AP'

# then, in Route A's installer:
#   AP_IFACE="wlan1"      <-- the dongle is already a real interface
# and delete the 'iw dev ... interface add' + MAC lines from uap0-up.sh;
# keep the unit only if you still want the rfkill/wait-for-device guard.

Pin the name so it cannot swap with the built-in radio across reboots — match on the dongle's own MAC:

cat /sys/class/net/wlan1/address        # e.g. 00:c0:ca:11:22:33

sudo tee /etc/udev/rules.d/70-wifi-names.rules <<'EOF'
SUBSYSTEM=="net", ACTION=="add", ATTR{address}=="00:c0:ca:11:22:33", NAME="wlanap"
EOF
sudo reboot

Then use wlanap as AP_IFACE. With two radios you can also run the AP on 5 GHz — though not for ESP32s, which are 2.4 GHz only.

9Point an ESP32 at it

Nothing special is required on the ESP32 side — the AP is an ordinary WPA2 network. The Pi is always at the fixed address, so hard-code it and skip discovery:

// ESP32 joins the Pi's concurrent AP. The Pi's IP never moves, so no mDNS needed.
const char* AP_SSID = "RPi_AP";
const char* AP_PASS = "raspberry123";
const char* PI_URL  = "http://192.168.50.1:8080/ingest";

WiFi.mode(WIFI_STA);
WiFi.setSleep(false);              // power save adds seconds of latency to POSTs
WiFi.begin(AP_SSID, AP_PASS);
while (WiFi.status() != WL_CONNECTED) { delay(500); Serial.print('.'); }
Serial.printf("\nESP32 %s -> Pi %s\n",
              WiFi.localIP().toString().c_str(), PI_URL);
Bind your Pi-side server to 0.0.0.0, not 192.168.50.1. Then the same service answers on the AP and on the station link — the ESP32s reach it over uap0 while you reach it from your laptop over the house network. Flask: app.run(host="0.0.0.0", port=8080).

12Uninstall

Removes both routes and returns wlan0 to a plain station.

#!/usr/bin/env bash
# Undo the concurrent AP. wlan0 and your station profile are left alone.
set -uo pipefail

# Route A
sudo nmcli connection down rpi-ap 2>/dev/null
sudo nmcli connection delete rpi-ap 2>/dev/null

# Route B
sudo systemctl disable --now hostapd dnsmasq 2>/dev/null
sudo rm -f /etc/dnsmasq.d/uap0.conf \
           /etc/systemd/system/{hostapd,dnsmasq}.service.d/override.conf \
           /etc/NetworkManager/conf.d/unmanaged-uap0.conf \
           /etc/sysctl.d/99-ap-sta-forward.conf

# shared parts
sudo systemctl disable --now uap0.service ap-channel-follow.timer 2>/dev/null
sudo rm -f /etc/systemd/system/uap0.service \
           /etc/systemd/system/ap-channel-follow.{service,timer} \
           /usr/local/sbin/{uap0-up.sh,ap-channel-follow.sh} \
           /etc/default/rpi-ap-sta
sudo iw dev uap0 del 2>/dev/null

sudo systemctl daemon-reload
sudo systemctl reload NetworkManager 2>/dev/null
iw dev            # only wlan0 should remain

If you used Route B's NAT, also drop the rules: sudo iptables -t nat -F POSTROUTING && sudo iptables -F FORWARD && sudo netfilter-persistent save. And if you appended denyinterfaces uap0 to /etc/dhcpcd.conf, remove that line by hand.
