ESP32 Beam & Stick — on-device web config portal

Each unit now publishes its own Wi-Fi network and a web page. Connect to it with a phone, read the live angle (and the GNSS fix on the stick), and type the field Wi-Fi credentials, the Raspberry Pi address and the length of the arm that unit is bolted to. The length is handed to the Pi once and confirmed.

1What you can do now

Nothing about the depth system's behaviour changed: both units still POST raw angles to the Pi, the stick still posts its GNSS fix, and the Pi still owns the geometry and computes depth = L1·sin(boom) + L2·sin(stick). What is new is that each unit is also a web server, always, on its own access point.

Why an access point and not just the field Wi-Fi? The radio runs in WIFI_AP_STA mode, so the unit joins the site router and keeps its own AP up at the same time. That means a mistyped Wi-Fi password is never fatal: the AP is still there, so you re-open the same page and fix it. No USB cable, no reflash, no climbing on the machine with a laptop.

3Build & flash

Nothing new to install. From each project folder:

cd "documents for learning/ESP32_Beam"
pio run                 # compile
pio run -t upload        # flash
pio run -t upload -t monitor   # flash and watch the serial log @115200

Then the same in documents for learning/ESP32_Stick. Both are verified to compile clean (no warnings) against the installed Arduino-ESP32 core 2.0.17.

Careful with pio run -t erase. Erasing the flash also wipes the nvs partition, which is where the unit keeps the SSID, password, Pi address and arm length. After an erase the unit falls back to the DEF_* constants at the top of main.cpp and the length counter goes back to 0 — you have to re-enter the length on the web page. A plain pio run -t upload only replaces the app and keeps your settings.

4Provision a unit (step by step)

  1. Power the unit. Watch the serial log — after ~1 s you get the line that tells you everything: 
    [web] config portal up: SSID 'EXCAV-BEAM' pass 'excav1234' -> http://192.168.4.1/
      (also http://beam.local/ once on the field wi-fi)
[web] saved config: field ssid 'A 3'  pi 192.168.0.110:5000  arm length 1100 mm
      (seq 0, never set on the web page)
  2. On a phone or laptop, join the Wi-Fi network EXCAV-BEAM (password excav1234). Your device will warn about "no internet" — that is expected; tell it to stay connected.
  3. Open http://192.168.4.1/. On the stick it is http://192.168.5.1/. The page starts updating once a second.
  4. Confirm the Angle card is moving when you tilt the arm, and that MPU6050 shows DMP READY. If it says no data, the sensor is not wired — fix that before anything else.
  5. Fill in the Settings card:
    • Field Wi-Fi SSID — the network the Pi is on. Press Scan for networks and pick it from the list to avoid typos (the site SSID A 3 has a space in it, which is easy to get wrong by hand).
    • Field Wi-Fi password — leave blank to keep the stored one.
    • Raspberry Pi IP and Port — the Pi's address on that network, port 5000 for monitoring_control.py. Reserve a static DHCP lease for the Pi on the router so this never moves.
    • Length of the arm THIS unit is bolted to, in millimetres, 100–20000. The beam unit's number becomes the Pi's L1, the stick unit's becomes L2.
  6. Press Save & apply. The green SAVED badge appears with a note of what happened, e.g. "length queued for the Pi (seq 1). re-joining wi-fi 'A 3'."
  7. Wait a few seconds and check the Links card: field wi-fi should flip to JOINED with an IP and a signal reading. Then the Arm length → Raspberry Pi card should turn CONFIRMED BY PI.
  8. Repeat for the other unit on its own AP. Do not skip this: the beam and the stick each store their own length.
If the page freezes right after Save & apply — that is normal and harmless. An ESP32 has one radio, so when the station link joins the router the access point moves to the router's channel and your phone gets bumped off. Re-join EXCAV-BEAM and reload. Nothing was lost; the save already happened.

The beam unit has no GNSS hardware, so its page hides the location card entirely. Position for the machine comes from the stick's SIM7000G, and the Pi serves both in GET /status under location.

6The one-shot length hand-off

You asked for the length to be sent once, with a confirmed transmission. That is exactly the contract:

you
Type 4200 in the length box on the beam's page and press Save & apply.
beam
Stores 4200 mm in NVS, bumps its edit counter (len_seq) to 1 and marks the length unconfirmed.
beam
POST /length {"id":"beam","len_mm":4200,"seq":1,"ip":"192.168.0.61"}
pi
Sets L1 = 4.2 m, writes it to monitoring_state.json, mirrors it into the value the DWIN settings page prefills from, and answers {"ok":true,"applied_mm":4200,...}.
beam
Marks the length confirmed (also in NVS) and never sends it again. The page shows CONFIRMED BY PI.

Only two things ever restart that sequence:

  • The Pi did not answer. Then the unit retries every 5 s — and only then. So a length typed while the Pi was powered off still lands the moment the Pi comes up. The page shows PENDING with the attempt count and the last HTTP code.
  • The Pi lost it. Every /ingest carries the unit's edit counter. If the Pi's stored counter does not match (state file deleted, Pi replaced, SD card reimaged), the /ingest reply carries need_length: true and the unit re-runs the hand-off by itself. This costs nothing in the normal case — the counter is 4 bytes on a post that already happens once a second.

What it looks like in the logs

On the unit's serial monitor:

[web] config saved: ssid='A 3' pi=192.168.0.110:5000 len=4200 mm seq=1
      -- length queued for the Pi (seq 1).
[len] 4200 mm (seq 1) CONFIRMED by the Pi at 192.168.0.110:5000 -- will not be sent again

...and if the Pi is not there yet:

[len] push of 4200 mm (seq 1) to 192.168.0.110:5000 failed (HTTP -1) -- retry in 5 s

On the Pi:

[len] beam web page assigned 4200 mm (4.200 m) seq=1 -> L1   geometry now
      L1=4.200 m L2=2.500 m (persisted to /home/pi/.../monitoring_state.json)
[hmi] adopted external geometry: L1=4.200 m L2=2.500 m (settings page will prefill with it)

And the self-healing case, after you wipe the Pi's state file:

[len] beam reports length edit seq=1 but we have seq=-1 -- asking it to re-send (need_length)
[len] beam web page assigned 4200 mm (4.200 m) seq=1 -> L1   geometry now ...
A never-provisioned unit sends nothing. The edit counter starts at 0 and 0 means "no length was ever typed on this unit's page". The Pi ignores it and never asks. That is deliberate: otherwise a freshly flashed spare unit would push its compiled-in 1100 mm default and quietly overwrite a length you had set on the DWIN panel.

Who wins when two places set the length

There are now three ways a length can arrive: a unit's web page (POST /length), the DWIN settings page (SAVE), and POST /config / the CLI --l1/--l2. The rule is simply last writer wins, and every write is logged with the resulting L1/L2 pair so the log always tells you what the depth model is using.

One subtlety I had to handle: the DWIN BACK key reverts the geometry to whatever was live when the operator opened the settings page. Without a fix, a length pushed from a unit mid-session would be silently undone by the next BACK. So /length and /config now call HmiController.note_external_length(), which adopts the new value as the revert baseline — unless the settings page is open right then, in which case the operator's in-progress entry stays authoritative and a log line says so.

Want the panel to be the only source of geometry? Start with --no-esp-length. Then POST /length is refused with HTTP 409, the /ingest reply never asks for a length, and the units' web pages become angle/GNSS/Wi-Fi displays only. Their Save & apply still works locally — the length just stays on the unit and shows as PENDING.

New in GET /status

{
  "boom_deg": 34.56, "stick_deg": -12.30, "depth_m": 1.482,
  "L1": 4.2, "L2": 2.5,                        <-- geometry actually in use (m)
  "esp_lengths": {                              <-- what each unit reported
    "beam":  {"mm": 4200.0, "seq": 1, "age_ms": 91234, "ip": "192.168.0.61"},
    "stick": {"mm": 2500.0, "seq": 1, "age_ms": 88010, "ip": "192.168.0.62"}

The ip values come from the ip field the units now include in every /ingest, which is the easy way to find a unit's web page once it is on the field Wi-Fi: curl -s http://<pi>:5000/status | python3 -m json.tool. Existing consumers (excavation_monitor.py, the DWIN driver, the GEOMind uploader) are unaffected — nothing was removed or renamed.

8HTTP API reference

On each ESP32 unit

RoutePurpose
GET /The page. Any unknown URL redirects here.
GET /api/liveEverything the page shows: imu, net, gps, cfg, sys.
GET /api/configSaved settings. Never returns the stored Wi-Fi password — only pass_set: true|false.
POST /api/configApply + persist. Accepts JSON or form fields. Absent keys (and empty ssid/pass/host) are left alone, so partial updates are fine.
GET /api/scanAsync scan: returns {"scanning":true} while it runs, then the SSID list. Poll it.
POST /api/resendClear the confirmation so the length is pushed to the Pi again.
POST /api/rebootRestart the unit.

So you can provision a unit from a script instead of a browser:

# set just the length (the beam is on its own AP at 192.168.4.1)
curl -X POST http://192.168.4.1/api/config \
     -H 'Content-Type: application/json' -d '{"len_mm":4200}'

# set everything at once
curl -X POST http://192.168.4.1/api/config -H 'Content-Type: application/json' \
     -d '{"ssid":"A 3","pass":"98832988","host":"192.168.0.110","port":5000,"len_mm":4200}'

# form encoding works too
curl -d 'len_mm=4200' http://192.168.4.1/api/config

# an OPEN field network needs the explicit clear (an empty "pass" means "keep")
curl -X POST http://192.168.4.1/api/config -H 'Content-Type: application/json' \
     -d '{"ssid":"OpenSite","pass_clear":true}'

# read the live state
curl -s http://192.168.4.1/api/live

On the Raspberry Pi

RoutePurpose
POST /lengthNEW {"id":"beam"|"stick","len_mm":4200,"seq":1,"ip":".."} → beam sets L1, stick sets L2. Answers {"ok":true,"applied_mm":..,"seq":..,"L1":..,"L2":..,"repeat":..}. Outside 100–20000 mm, or a bad id, gives HTTP 400 and changes nothing. A repeat of an already-applied seq is acked again with repeat:true — a lost ACK must not leave the two sides disagreeing.
POST /ingestEXTENDED Also reads ip and len_seq. The reply gained need_length. The angle handling is untouched.
GET /statusEXTENDED Gained esp_lengths, L1, L2. Nothing removed.
POST /location, POST /config, POST /rfid, POST /hse SAMEUnchanged.
 
# push a length by hand, exactly as a unit would
curl -X POST http://192.168.0.110:5000/length -H 'Content-Type: application/json' \
     -d '{"id":"beam","len_mm":4200,"seq":99}'

# see the geometry in use and what each unit reported
curl -s http://192.168.0.110:5000/status | python3 -m json.tool

9Verification checklist

Six checks, in order. Each one has a specific thing to look for.

#DoExpect
1Power a unit, watch the serial log[web] config portal up: SSID 'EXCAV-BEAM' ... http://192.168.4.1/
2Join that AP, open the IPThe page loads and the angle numbers move when you tilt the sensor
3Enter the site SSID / password / Pi IP, press Save & applyfield wi-fi → JOINED with an IP; on the Pi, [ beam] angle=… lines start
4Enter the arm length, press Save & applyUnit: [len] … CONFIRMED by the Pi. Pi: [len] beam web page assigned 4200 mm … -> L1. Page: CONFIRMED BY PI
5curl -s http://<pi>:5000/statusL1 is your beam length in metres, esp_lengths.beam.mm matches what you typed, and depth_m changes as the arm moves
6Stop the Pi, delete monitoring_state.json, start it againWithin a second or two: [len] beam reports length edit seq=1 but we have seq=-1 -- asking it to re-send, immediately followed by the length being re-applied. Nobody had to touch the machine.
Already verified here: both firmwares compile clean with zero warnings; the embedded page's markup, ids and JavaScript were parsed and the page render was exercised against the exact JSON the firmware produces; and the /length + need_length handshake was run end-to-end against both Pi receivers — first push, duplicate push, out-of-range and junk values, unknown ids, stick→L2, state-file persistence and --no-esp-length all behave as described. What could not be tested without hardware is the radio itself: the AP coming up, the DMP, and the SIM7000G.

10Troubleshooting

SymptomCause / fix
The AP does not appearGive it ~10 s: the MPU calibration runs first. If it still does not, check the serial log for the [web] config portal up line — without it, fieldcfg_begin() never ran.
The page loads but never updatesfieldcfg_handle() is not being called. On the beam it lives in loop(), on the stick in angleTask. A blocking call added elsewhere in that task will starve it.
The page dies the moment I press SaveExpected — the AP followed the router to a new channel. Re-join EXCAV-BEAM and reload; the save already happened.
Wi-Fi never joinsCheck the SSID for a hidden space (the site SSID is literally A 3) and use Scan for networks. 2.4 GHz only — an ESP32 cannot see a 5 GHz SSID.
Length stays PENDINGRead last attempt on the page. HTTP -1 = the Pi is not answering on that IP:port (wrong address, Pi down, different subnet). HTTP 409 = the Pi was started with --no-esp-length. HTTP 400 = the length is outside 100–20000 mm.
The Pi keeps asking for the lengthIt is failing to persist. Check that monitoring_state.json is writable — save_state() prints [state] write failed: when it is not.
Depth looks frozen or absurdCheck L1/L2 in GET /status. The classic cause is a length entered in metres where millimetres were expected; /length refuses anything under 100 mm precisely to stop that.
Wrong unit's pageThe beam is 192.168.4.1 on EXCAV-BEAM, the stick is 192.168.5.1 on EXCAV-STICK. The page title and the device id line under it also say which one you have.
beam.local does not resolvemDNS only works once the unit has joined the field Wi-Fi and your device is on the same network. Over the config AP always use the numeric IP.
Settings vanished after a flashYou ran -t erase (or erase_flash), which wipes NVS. Re-enter them; plain -t upload keeps them.

11Limits & things to know

  • Security is deliberately minimal. WPA2 on the AP with a shared password and no login on the page. Anyone within Wi-Fi range who knows excav1234 can change the arm length and the Pi address. Change the AP password in the FIELD_ID block of each main.cpp before this goes anywhere public, and note that the field Wi-Fi password is write-only through the API — the page can set it but never reads it back.
  • The two web_config files must stay byte-identical. Nothing enforces it. After editing one, copy both files to the other project: cp ESP32_Stick/src/web_config.* ESP32_Beam/src/.
  • One radio, one channel. AP+STA share it, so the AP hops when the station joins, and heavy AP traffic and the 1 Hz telemetry compete. Fine at this data rate; do not stream video through it.
  • The beam has no GNSS. Its page hides the location card. If you want the beam to show a position too, the honest options are to fit it a GNSS module or to have its page read the Pi's /status — the latter needs the Pi reachable from whatever is viewing the page.
  • The length is one-shot by design. It is not re-sent on every post, so if you change L1/L2 on the Pi (panel, /config, CLI) the unit will not argue — the Pi's value simply stands. Press Re-send length to the Pi on the unit if you want the unit's number to win again.
  • The Pi's /length route has no authentication, exactly like the existing /ingest, /config and /rfid routes. It is bound to the field network; keep that network closed.
