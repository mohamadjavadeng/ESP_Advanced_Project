2Run your code at startup

"How do I put my code in the startup of the Raspberry Pi?"

Use systemd. There are four ways to autostart something on a Pi and only one of them handles the things your program actually needs — a working directory, an environment variable for the API key, serial-port group membership, ordering after the access point, and an automatic restart when it crashes at 3 a.m. in a quarry.

MethodRestarts on crash?Ordering / deps?Logs?Verdict
/etc/rc.localNoNoNoDeprecated not present on Bookworm by default
crontab @rebootNoNoYou redirect by handToy no env, no ordering
Desktop autostartNoNoNoWrong needs a graphical login session
systemd unitYesYesjournaldUse this

Step 1 — put the API key in a root-only file

Keeping it out of the unit file means it does not show up in systemctl cat and does not get copied around when you share the service definition.

sudo install -m 600 -o root -g root /dev/null /etc/excavator-monitor.env
sudo nano /etc/excavator-monitor.env
# /etc/excavator-monitor.env   (chmod 600, root:root)
GEOMIND_APIKEY=your_pdo_device_service_key_here

systemd reads EnvironmentFile= as root, before it drops to User=pi, so mode 600 root:root is both safe and workable.

Step 2 — the unit file

sudo nano /etc/systemd/system/excavator-monitor.service
[Unit]

[Service]

# /dev/serial0 (the DWIN panel) is owned by root:dialout.

# resolved against this directory. Without it the service dies on ImportError.

# Without this, Python block-buffers stdout when it is a pipe and `journalctl -f`
# shows nothing for minutes. This is the single most common "my service is dead"
# false alarm.

    --http-port 5000 \
    --dwin-port /dev/serial0 --dwin-baud 115200 \
    --geomind-host https://app.geo-mind.ai \

[Install]
WantedBy=multi-user.target
Adjust two things for your machine. Replace pi with the output of whoami, and the WorkingDirectory with the output of pwd run inside your raspberry_pi/ folder. If you installed the dependencies into a virtualenv, point ExecStart at that interpreter instead — /home/pi/venv/bin/python3 — and drop the python3 from the argument list.

Free the serial port first, or the DWIN panel will never answer. By default the Pi puts a login console on the UART. 3Wait for Wi-Fi before running

"How can I tell the Raspberry Pi to wait until the Wi-Fi connection is established, then run these codes at startup?"

The literal answer is two lines, and I give it below. But read the box first, because for your program the literal answer is usually the wrong thing to do.

You mostly do not need to wait at all. Your server binds 0.0.0.0:5000. Binding to 0.0.0.0 succeeds even when the Pi has no network at all — the socket simply accepts connections on whatever interfaces appear later. You would only need to block on the network if you bound a specific IP (--http-host 192.168.50.1), because that address has to exist at bind() time or Python raises OSError: [Errno 99] Cannot assign requested address. Same story for the cloud thread: it already catches failures and retries, and the docstring is explicit that the excavator keeps working — depth, alarm, buzzer — with no network.

The literal answer

systemd has two different targets and the difference is the whole question:

TargetMeansGood enough to POST?
network.targetThe network management stack has started. Interfaces may still be down and have no IP.No
network-online.targetAt least one connection is fully up with an address. Only reached if a unit pulls it in.Yes
 
[Unit]
# BOTH lines are required. `After=` alone only orders you behind the target --
# it does not cause the target to be reached. `Wants=` is what actually pulls in
# NetworkManager-wait-online.service (or systemd-networkd-wait-online).
Wants=network-online.target
After=network-online.target
Two traps with network-online.target on a field machine.
  1. It is satisfied by any managed connection, including a link that has an IP but no route to your Pi and no internet. "Online" here means "an interface came up", not "the thing you care about is reachable".
  2. It blocks boot when there is no modem. nm-online waits its full timeout (30–60 s depending on version) before giving up. On an excavator parked out of coverage, that is a minute of dead panel on every power-up, for nothing.

The better answer: wait for what you actually need

Drop a small script that waits for a specific, checkable condition, and — this is the important part — always exits 0, so a timeout logs a reason instead of refusing to start the excavator.

sudo nano /usr/local/sbin/wait-for-net.sh
sudo chmod +x /usr/local/sbin/wait-for-net.sh
#!/bin/bash
# Block until the Pi has what the caller actually needs, then get out of the way.
#   $1 = ap | lan | internet     (default: ap)
#   $2 = timeout in seconds      (default: 60)
#
# Exits 0 even on timeout, ON PURPOSE: used as ExecStartPre=, a non-zero exit
# would refuse to start the depth monitor -- and the excavator must run offline.
set -u
PATH=/usr/sbin:/usr/bin:/sbin:/bin
what=${1:-ap}; timeout=${2:-60}; t0=$SECONDS

while [ $((SECONDS - t0)) -lt "$timeout" ]; do
  case "$what" in
    ap)       ip -4 addr show uap0 2>/dev/null | grep -q 'inet ' && exit 0 ;;
    lan)      ip -4 route show default | grep -q .               && exit 0 ;;
    internet) ping -c1 -W2 1.1.1.1 >/dev/null 2>&1               && exit 0 ;;
  esac
  sleep 1
done

logger -t wait-for-net "timed out after ${timeout}s waiting for '$what' -- starting anyway"
exit 0

Wire it in — this line is already in the unit in section 2:

ExecStartPre=/usr/local/sbin/wait-for-net.sh ap 45

Test it standalone before trusting it: time /usr/local/sbin/wait-for-net.sh ap 10; echo "exit=$?"

What the boot sequence looks like once it is wired up

systemd boot │ ├─ network.target ................ NetworkManager running │ ├─ ap-sta.service ................ creates uap0, gives it 192.168.50.1 ◀── from ap_sta_setup.py │ │ │ ├─ hostapd.service ....... starts broadcasting "RPi_AP" │ └─ dnsmasq.service ....... starts handing out .10 - .100 leases │ └─ excavator-monitor.service ..... After= all of the above │ ├─ ExecStartPre: wait-for-net.sh ap 45 (uap0 has an IP? go) └─ ExecStart: monitoring_control.py --http-port 5000 ... │ └─ binds 0.0.0.0:5000 ─── ESP32s POST /ingest cloud thread retries app.geo-mind.ai in the background, whether or not the modem ever shows up

Other ways, if you prefer them

# A. NetworkManager's own wait tool, inline (Bookworm / any NM system):
ExecStartPre=/usr/bin/nm-online -s -q --timeout=60

# B. Wait for a specific host to answer, not merely for "a network":
ExecStartPre=/bin/bash -c 'until ping -c1 -W1 192.168.50.1 >/dev/null 2>&1; do sleep 1; done'
#    Beware: no timeout -> this hangs boot forever if that host never appears.

# C. A dispatcher hook that fires the moment NM brings a link up (event, not poll):
#    /etc/NetworkManager/dispatcher.d/50-excavator   (chmod 755, root:root)
#!/bin/sh
[ "$2" = "up" ] && systemctl start excavator-monitor
exit 0

4A fixed Pi IP the ESP32s can hard-code

"How can I make my RPi4 the Wi-Fi station with a constant IP that I put in my ESP32, to avoid initial configuration every time the Pi connects to a different modem?"

This is the right question to be asking, and the repo already contains the right answer. The problem is structural: while the Pi is a client of somebody else's modem, that modem picks the subnet and the address. New modem, new subnet, and the DEF_RPI_HOST baked into both ESP32s is instantly wrong. No amount of static-IP configuration on the Pi fixes that, because 192.168.0.110 is not even a valid address on a modem that hands out 10.0.0.x.

Invert it. Stop being a guest on the modem's network — own the network the ESP32s join. Make the Pi the access point. Then the Pi's address on that network is a constant you choose, and it is completely independent of which modem, if any, the Pi is also connected to.

BEFORE (Pi is a guest — breaks on every modem change) modem A: 192.168.0.x modem B: 10.0.0.x phone hotspot: 172.20.10.x │ │ │ └── Pi = 192.168.0.110 └── Pi = 10.0.0.57 └── Pi = 172.20.10.4 ESP32 hard-coded ESP32 still says ESP32 still says 192.168.0.110 ✔ 192.168.0.110 ✘ 192.168.0.110 ✘ AFTER (Pi owns the network the ESP32s join — modem is irrelevant) any modem / any hotspot / no modem at all │ └── wlan0 (client, whatever IP it gets — nobody cares) Raspberry Pi ── one radio ── └── uap0 = 192.168.50.1 ◀── ALWAYS. Hard-code this in both ESP32s. │ ├── EXCAV-BEAM → DHCP 192.168.50.10 └── EXCAV-STICK → DHCP 192.168.50.11

Step 1 — bring the AP up (already scripted for you)

cd ~/ESP_Advanced_Project/raspberry_pi
sudo python3 ap_sta_setup.py
sudo reboot

That gives you, permanently and across reboots:

SettingValueChange it in

The subnet choice is already correct — keep it. 192.168.50.x deliberately does not collide with the BEAM's own SoftAP (192.168.4.1) or the STICK's (192.168.5.1). If you ever change AP_IP, stay off 192.168.4.x and 192.168.5.x, or a laptop sitting on both networks will route to the wrong device.

Step 2 — point the ESP32s at it

In both ESP32_Beam/src/main.cpp and ESP32_Stick/src/main.cpp:

constexpr char     DEF_WIFI_SSID[] = "RPi_AP";          // was "A 3" / "AMAN 2"
constexpr char     DEF_WIFI_PASS[] = "raspberry123";
constexpr char     DEF_RPI_HOST[]  = "192.168.50.1";    // was "192.168.0.110"
constexpr uint16_t DEF_RPI_PORT    = 5000;              // unchanged
The trap that will cost you an hour: NVS beats the constants. Those DEF_* values are factory defaults only. Once anything has been saved on the unit's web portal, the saved copy lives in NVS and wins on every boot — reflashing does not clear it. You have already seen this: the boot log printed field ssid 'AMAN 2' while the source said "A 3".

Two ways out, pick one per unit:
  • Web portal — join EXCAV-BEAM, open http://192.168.4.1/, type the new SSID / password / Pi IP, save. No cable needed. Do the same on EXCAV-STICK at http://192.168.5.1/.
  • Wipe NVS so the new constants take effect: pio run -t erase && pio run -t upload. This also erases the saved arm length — re-enter it.

Confirm it worked

The serial monitor now prints the station IP on the join edge — that is the change we just made to both firmwares:

[wifi] connected to 'RPi_AP' -- ESP station IP 192.168.50.10  gw 192.168.50.1  RSSI -47 dBm

A gw of 192.168.50.1 proves the unit joined the Pi's AP and not some leftover modem.

5List every device connected to the Pi

"Can I configure my Raspberry Pi to find all the IPs that are connected to it?"

Yes — four ways, at three different layers. They answer slightly different questions, so knowing which is which saves you from chasing a device that is associated but has no lease.

LayerCommandAnswers
802.11 radiosudo iw dev uap0 station dumpWho is associated, with signal strength — even before DHCP
DHCPcat /var/lib/misc/dnsmasq.leasesWho got an IP, plus MAC and hostname
ARP / neighboursip neigh show dev uap0Who the Pi has actually talked to recently
Active scannmap -sn 192.168.50.0/24Anything alive, including static-IP devices with no lease

Lease file path depends on who runs the DHCP server. Your ap_sta_setup.py uses the system dnsmasq with a drop-in at /etc/dnsmasq.d/uap0.conf, so leases land in the Debian default, /var/lib/misc/dnsmasq.leases. If you ever switch to NetworkManager's built-in shared mode instead, they move to /var/lib/NetworkManager/dnsmasq-wlan0.leases. Same format either way.
You already have this, for free, without any of the above. Both firmwares put their own address into every telemetry POST — doc["ip"] = WiFi.localIP().toString() — so monitoring_control.py knows each unit's IP as a side effect of receiving angles. curl -s http://192.168.50.1:5000/status is the fastest check that matters, because it tells you not just "connected" but "connected and sending data". An ESP32 that shows up in station dump but not in /status has a Wi-Fi link and a broken HTTP path — a completely different bug from one that never associates.

A one-shot script that merges all three layers

nano ~/ESP_Advanced_Project/raspberry_pi/who_is_connected.py
chmod +x ~/ESP_Advanced_Project/raspberry_pi/who_is_connected.py
#!/usr/bin/env python3
"""Who is on the Pi's access point right now?

Merges the three layers that can disagree:
  radio  -- iw station dump   : associated, with RSSI (may have no IP yet)
  dhcp   -- dnsmasq.leases    : got an address (may have since walked away)
  arp    -- ip neigh          : actually exchanged packets recently

Run:  sudo python3 who_is_connected.py
(sudo only for `iw station dump`; the rest works unprivileged.)
"""
import pathlib
import re
import subprocess
import time

AP_IFACE   = "uap0"
LEASE_FILE = "/var/lib/misc/dnsmasq.leases"


def leases():
    """MAC -> (ip, hostname, expiry_epoch) from the dnsmasq lease file."""
    out = {}
    p = pathlib.Path(LEASE_FILE)
    if not p.exists():
        return out
    for line in p.read_text().splitlines():
        f = line.split()
        if len(f) >= 4:
            out[f[1].lower()] = (f[2], f[3], int(f[0]))
    return out


def stations():
    """MAC -> {'signal': '-47 dBm', ...} for everyone associated at the radio layer."""
    out, mac = {}, None
    try:
        txt = subprocess.check_output(
            ["iw", "dev", AP_IFACE, "station", "dump"], text=True)
    except Exception as exc:                 # not root, or uap0 does not exist
        print(f"  (!) iw station dump failed: {exc}")
        return out
    for line in txt.splitlines():
        m = re.match(r"Station ([0-9a-fA-F:]{17})", line.strip())
        if m:                                # the MAC line also contains colons,
            mac = m.group(1).lower()         # so match it BEFORE the k:v branch
            out[mac] = {}
        elif mac and ":" in line:
            k, _, v = line.partition(":")
            out[mac][k.strip()] = v.strip()
    return out


def neighbours():
    """MAC -> ip, from the kernel's ARP table (who we actually talked to)."""
    out = {}
    try:
        txt = subprocess.check_output(
            ["ip", "neigh", "show", "dev", AP_IFACE], text=True)
    except Exception:
        return out
    for line in txt.splitlines():
        # "show dev uap0" prints 4 fields (IP lladdr MAC STATE); a bare "ip neigh"
        # prints 6 (IP dev uap0 lladdr MAC STATE). Index off "lladdr" to take both.
        f = line.split()
        if "lladdr" in f and f[-1] not in ("FAILED", "INCOMPLETE"):
            out[f[f.index("lladdr") + 1].lower()] = f[0]
    return out


def main():
    lease, sta, arp = leases(), stations(), neighbours()
    macs = sorted(set(lease) | set(sta) | set(arp))

    if not macs:
        print(f"Nothing on {AP_IFACE}. Is hostapd running?  "
              f"systemctl status hostapd")
        return

    print(f"{'MAC':<19} {'IP':<16} {'NAME':<12} {'RSSI':>8}  {'IDLE':>7}  SEEN BY")
    print("-" * 78)
    for mac in macs:
        ip, name, exp = lease.get(mac, ("-", "-", 0))
        if ip == "-":
            ip = arp.get(mac, "-")           # static-IP client: no lease, but in ARP
        info = sta.get(mac, {})
        rssi = info.get("signal", "-").replace(" dBm", "")
        idle = info.get("inactive time", "-").replace(" ms", "")
        seen = "+".join(w for w, hit in
                        (("radio", mac in sta), ("dhcp", mac in lease),
                         ("arp", mac in arp)) if hit)
        left = f"{int(exp - time.time()) // 60}m" if exp else "-"
        print(f"{mac:<19} {ip:<16} {name:<12} {rssi:>8}  {idle:>7}  {seen}  lease {left}")


if __name__ == "__main__":
    main()

6Wi-Fi client and hotspot at the same time

"Can I use the Wi-Fi and hotspot capability of the Raspberry Pi at the same time?"

Yes. That is exactly what ap_sta_setup.py already does on your Pi 4, with a single radio and no extra hardware. The Broadcom chip supports one station link and one AP simultaneously; you just cannot expose that through a single interface name, so the script creates a second virtual interface on the same physical radio.

┌─────────────── Raspberry Pi 4 ───────────────┐ │ one physical radio (brcmfmac) │ modem / hotspot │ │ ────────wifi─────┼──▶ wlan0 STA (client) ── internet, cloud │ │ │ │ │ └── same chip, SAME CHANNEL │ │ │ ESP32 BEAM ─────┼──▶ uap0 AP 192.168.50.1 │ ESP32 STICK ─────┼──▶ hostapd + dnsmasq │ │ │ │ monitoring_control.py binds 0.0.0.0:5000 │ │ → reachable on BOTH interfaces at once │ └───────────────────────────────────────────────┘

Hardening: make the AP follow the client's channel automatically

Your README_AP_STA.md says to re-run the setup script after moving to a different router. You can automate that. This is the single most valuable addition for a machine that meets a new modem every week.

sudo nano /usr/local/sbin/ap-channel-follow.sh
sudo chmod +x /usr/local/sbin/ap-channel-follow.sh
#!/bin/bash
# Keep the uap0 access point on the same channel as the wlan0 client link.
#
# A one-radio Pi cannot run them on different channels. When wlan0 associates
# with a new modem on another channel, hostapd keeps advertising the OLD channel
# and the ESP32s silently stop being able to join. This re-syncs and restarts it.
set -u
PATH=/usr/sbin:/usr/bin:/sbin:/bin
CONF=/etc/hostapd/hostapd.conf

cur=$(iw dev wlan0 info | awk '$1=="channel"{print $2}')
[ -z "${cur:-}" ] && exit 0                    # wlan0 not associated: nothing to follow

want=$(awk -F= '$1=="channel"{print $2}' "$CONF")
[ "$cur" = "$want" ] && exit 0                 # already in sync, cheap no-op

logger -t ap-channel-follow "wlan0 moved to channel $cur (hostapd had $want) -- resyncing"
sed -i "s/^channel=.*/channel=$cur/" "$CONF"
systemctl restart hostapd
sudo nano /etc/systemd/system/ap-channel-follow.service
[Unit]
Description=Re-sync the uap0 AP channel to the wlan0 client channel
After=hostapd.service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/ap-channel-follow.sh
sudo nano /etc/systemd/system/ap-channel-follow.timer
[Unit]
Description=Check every minute whether wlan0 changed channel

[Timer]
OnBootSec=90
OnUnitActiveSec=60

[Install]
WantedBy=timers.target
sudo systemctl daemon-reload
sudo systemctl enable --now ap-channel-follow.timer
systemctl list-timers ap-channel-follow.timer      # confirm it is scheduled
journalctl -t ap-channel-follow -f                 # watch it work
The bulletproof alternative: a second radio. A ~£8 USB Wi-Fi dongle removes the shared-channel constraint entirely — run the AP on one radio and the client on the other, on independent channels, and delete the watchdog. In ap_sta_setup.py set AP_IFACE = "wlan1" and remove the iw dev wlan0 interface add line from the bring-up script (the dongle is already a real interface). Pin the name with a udev rule so it does not swap between wlan0 and wlan1 across reboots. If this Pi is going onto a machine you cannot easily reach, it is worth the £8.

7Bring-up order (do it in this sequence)

  1. Free the UART — raspi-config: serial console off, serial hardware on. Optionally dtoverlay=disable-bt. Reboot.
  2. Join the field Wi-Fi as a client (nmtui) so the AP script can detect a channel and the Pi has internet for the cloud thread.
  3. Set the country code in ap_sta_setup.py (COUNTRY) and in raspi-config → Localisation. A wrong regulatory domain silently kills transmit power.
  4. Run the AP setup — sudo python3 ap_sta_setup.py, then reboot. Verify: iw dev lists uap0, ip addr show uap0 shows 192.168.50.1, iw dev wlan0 link still shows the client link.
  5. Install the channel-follow timer (section 6).
  6. Repoint the ESP32s to RPi_AP / 192.168.50.1:5000 — remember NVS beats the constants (section 4).
  7. Test the program by hand first, in the foreground, so you see the tracebacks: cd ~/ESP_Advanced_Project/raspberry_pi && GEOMIND_APIKEY=... python3 monitoring_control.py --http-port 5000
  8. Only then install the systemd unit (section 2) and sudo systemctl enable --now excavator-monitor.
  9. Reboot and verify unattended — this is the real test: sudo reboot, wait, then systemctl status excavator-monitor, sudo python3 who_is_connected.py, curl -s http://192.168.50.1:5000/status.

8Troubleshooting

SymptomLikely causeCheck / fix
Service says active (running) but journalctl -f is empty Python is block-buffering stdout Add Environment=PYTHONUNBUFFERED=1
ModuleNotFoundError: No module named 'dwin_lcd' WorkingDirectory= missing or wrong Must be the raspberry_pi/ folder
FileNotFoundError: Driver_name_database.xlsx Same cause — the --driver-csv path is relative Fix WorkingDirectory=, or pass an absolute path
Permission denied: '/dev/serial0' Service user is not in dialout SupplementaryGroups=dialout, or sudo usermod -aG dialout pi
DWIN not responding at boot but fine by hand Serial console still owns the UART raspi-config → Serial Port → login shell No
Boot hangs ~60 s before the panel lights up network-online.target waiting for a modem that is not there Drop it; use wait-for-net.sh ap 45 (section 3)
OSError: [Errno 99] Cannot assign requested address Bound a specific IP before the interface existed Use --http-host 0.0.0.0, or wait for uap0
OSError: [Errno 98] Address already in use A hand-started copy is still holding :5000 sudo ss -lptn 'sport = :5000' then kill it
AP does not appear / ESP32 cannot join Channel drift after a modem change — the most common one iw dev wlan0 link vs channel= in the hostapd conf; install the follow timer
hostapd will not start It ships masked sudo systemctl unmask hostapd; journalctl -u hostapd -b
ESP32 associates but gets no IP dnsmasq not bound to uap0 journalctl -u dnsmasq -b; confirm ip addr show uap0
ESP32 has an IP but [post] failed Wrong host/port in NVS, or wrong receiver running ESP web portal; curl http://192.168.50.1:5000/status from the Pi
ESP32 joins the old modem after you changed the source NVS overrides DEF_WIFI_SSID Web portal, or pio run -t erase
Weak range / clients drop at full reach Wrong country code ⇒ reduced TX power COUNTRY in ap_sta_setup.py + raspi-config; check RSSI with who_is_connected.py
